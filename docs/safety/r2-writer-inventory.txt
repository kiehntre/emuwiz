Method and visibility limits
----------------------------

The workspace comprises archivefs-core, archivefs-cli and archivefs-gui. I traced
writer entry points, their publication and reversal helpers, and normal GUI/CLI
call sites across these crates. baseline-mutation-search.json records the exact
baseline object and heuristic raw search hits in 157 source files. It is a search
index, NOT a count of 157 writer engines or a completeness proof. The heuristic
excludes named test files and suffixes following a cfg(test) module; inline test
helpers can still appear, and production code after a test module, alias/member
calls, unsafe syscalls and external subprocess writes need separate inspection.

The family inventory below is the manually audited set. I distinguish actual
application callers, callable exported APIs with no application caller found,
explicitly refused paths, and non-game resources. 'No caller found' means static
search of this workspace, not an assertion that a public API is uncallable.
There was no dynamic trace of every UI action, external binary or operating
system platform. Generated code, future code, separately built consumers, old
installed binaries, other applications and externally spawned emulator behavior
are outside this source inventory's visibility. This report cannot prove that
every possible managed-file write is intercepted.

References beginning core/, cli/ or gui/ expand to
crates/archivefs-core/src/, crates/archivefs-cli/src/, or
crates/archivefs-gui/src/. All line numbers are baseline references.

Production compiles compact read/materialization dispatch. Production reads of
compact evidence do not establish mutation authority.

admission::Configuration, acquires admission, records claims and reserves the

ACTIVE checkpoint adapter (:21-38) is not application bootstrap. The restrictions
at :116-150 require a new Planned transaction, 1-8 Planned regular-file
RenameMove entries, no created directories, no recovery resolution or exact-

Config-only, metadata-only and read-only categories
-------------------------------------------------

These writes should be recorded, but grouping them with game payload operations
merely because they call fs::write or a common atomic helper would misstate scope:

* CLI rom-organise only manages master-root configuration.
* GUI preferences/page state (e.g. rom_organisation_page.rs:776-822), setup
  overrides, onboarding, bezel preferences, cheat reconciliation persistence,
  view modes and library/provider configuration.
* Identity/provider snapshots, DAT downloads/audit caches, archive index
  (lib.rs:6984), art/thumbnail/PDF caches, mod downloads, cheat catalogues,
  database/catalogue updates, database backup/restore and setup portability.
  Some metadata influences later game mutation, so it is not semantically
  irrelevant; it is not itself a selected game payload write.
* read-only probes in storage_conversion.rs, archive RAR/LHA member inspection,
  laserdisc verification, CUE evidence inspection and private temporary
  inspection data (including amiga_adz.rs) are not game mutation engines.
* mame_collection_analyser/corrections.rs and several regression-labelled files
  in the raw hit list are test support, not user writer entry points.
* Generic atomic_text, noclobber, dirsync and filesystem helper functions are
  primitives shared by unrelated domains. Guarding a primitive does not supply
  the transaction's complete object/name set or recovery/approval lifecycle.

Smallest feasible integration assessment
----------------------------------------

There is no truthful small change that makes all current GUI/CLI/background
managed-file writers participate in the accepted R2 authority while also leaving
R2 mutation disabled and introducing no new authority/engine. The authority is
test-private, has no application bootstrap, and the Bridge deliberately cannot
represent most operations above. Removing cfg(test), selecting a global lock
directory, or adapting unsupported operations implicitly is production/security
design work, not a wrapper-only correction.

A hook around the ordinary rename executor could at most establish a bounded
test-only property for supported operations. It misses exact-resume and
quarantine direct loops, separate writer engines, staging/cleanup outside the
hook, background and nested operations, backup/sidecar names, and recovery paths.
Checking compact descriptors alone cannot discover a selected object's other
aliases or claims in another directory. A separate 'legacy cooperative' lock
would be a second authority unless it is explicitly the same designed authority
with a defined enrollment/ownership lifecycle; it cannot be advertised as R2
whole-application participation by analogy.

Production same-version cooperation needs an explicit design for: shared
GUI/CLI/background authority selection independent of profile/journal path;
trusted registration/bootstrap and restart context; complete object and both-
name/backup/sidecar/directory alias sets; operation scopes that span checks,
publication, checkpoints, compensation and cleanup; nested/reentrant ownership;
failure/uncertain-state claims retained until demonstrated terminal release;
and adapters for the other journal models. The present regular-move Bridge does
not supply those contracts for these families. Old/unaware/external writers and
retained writable descriptors remain outside voluntary participation even after
current-version enrollment, absent separately approved custody controls.

The smallest justified bounded work now is to fix the confirmed Undo reporting
and receipt-retention bugs, preserve the R2 disabled gate, retain this source
inventory, and produce actual current/current legacy and old/external race
characterizations with honest NOT PREVENTED outcomes. Further tests using the
existing authority can prove narrowly enrolled test workers; they must not be
presented as protection for production GUI/CLI writers. If whole-app cooperation
is mandatory, this is a substantial architecture boundary requiring the owner's
explicitly approved design and later independent review, not completion by
claiming an executor-only guard covers every writer.
