## 1. Current code findings

`crates/archivefs-core/src/memory_card_inventory.rs` (273 lines, read in full by the calling session before this audit was commissioned) is a read-only PS1/PS2 memory-card inventory module. Its module doc states plainly: "the card image is always the shared preservation unit... this module never extracts, rewrites, repairs, or attributes a complete card to one game."

**PS1 path (`inspect_ps1`)** is fully implemented: fixed 15-slot table, per-block header-byte classification (`0xA0`/`0x51` occupied, `0xA1`–`0xA3` deleted, anything else → damaged, never guessed), XOR checksum validation (byte 127 against bytes 0–126) that only reports mismatches, never repairs them, and identity extraction from header bytes 12–22 (product code, `ConfirmedIdentity` only if it contains a `-`) or a save-title text field (`SupportingEvidence`), never promoting a title string alone to confirmed identity.

**PS2 path (`looks_like_ps2` + `inspect_memory_card`)** is deliberately minimal. `looks_like_ps2()` checks only whether the first 30 bytes, read as UTF-8, start with the literal string `"Sony PS2 Memory Card Format"`. That is the entire PS2 detection logic today — no page-size field is read, no superblock is parsed, no version field is parsed, no cluster/FAT logic exists. When that one check matches, `inspect_memory_card()` returns a `MemoryCardInventory` with `format: Ps2`, `format_confidence: ConfirmedFormat`, `health: UnsupportedVariant`, `entries: Vec::new()` (deliberately empty), and the warning string "PS2 card header is recognized, but filesystem allocation/directory semantics are not yet independently proven; no entries were guessed." Every returned inventory — PS1 or PS2 — sets `shared_container: true` unconditionally, enforcing the whole-card-is-the-unit design at the type level for every code path.

There is an existing regression test, `ps2_header_is_not_falsely_enumerated`, that writes an 8 MiB buffer with the PS2 magic string and an all-zero payload and asserts `format == Ps2`, `health == UnsupportedVariant`, `entries.is_empty()` — i.e. the codebase already has a test specifically guarding against ever silently starting to enumerate PS2 entries from header recognition alone. Two other tests cover the PS1 round-trip (confirming source bytes are never modified) and truncated/unknown inputs failing closed.

**What the current PS2 code proves:** a file's first 30 bytes are the ASCII string `"Sony PS2 Memory Card Format"` (case-sensitive, exact substring at offset 0). That is the entire proof.

**What it does not prove:** page size, cluster size, any superblock field value, FAT/allocation structure, directory structure, any file/save identity, any timestamp, any size, or whether the card is structurally valid beyond that one string being present. `entries` is always empty for a recognized PS2 card; `used_blocks`/`free_blocks` are always `None`.

**Integration:** `pub mod memory_card_inventory;` is declared in `crates/archivefs-core/src/lib.rs` (line 103). A repo-wide grep for `memory_card_inventory` outside this one file found no callers — it is not wired into any GUI page, CLI command, or other module yet. A repo-wide grep for `save_vault` / `savevault` / `SHARED_MEMORY_CONTAINER` / `shared_container` outside this file also found zero matches anywhere else in the repo. **"Save Vault" as a named feature and "SHARED_MEMORY_CONTAINER" as a named cross-module principle do not exist as implemented code, or even as a string, anywhere else in the repository.** `shared_container: bool` is this module's own local field name, not (yet) a shared cross-module concept. Any reference to "Save Vault" elsewhere in this document (or in the task that produced it) is aspirational/contextual framing, not a description of running code — stated here plainly so this document is not mistaken for evidence that Save Vault exists.

## 3. Raw card geometry

- **Page size:** 512 bytes of user data per page is the PS2 standard (`page_len` superblock field, default value 512; confirmed independently as `PS2MC_STANDARD_PAGE_SIZE = 512` in `mymc`'s constants).
- **Spare/ECC bytes:** 16 bytes of spare area per 512-byte page is the standard raw+ECC figure. This **matches the local-evidence arithmetic already independently derived by the calling session** from a real PCSX2-generated card: 8,650,752 bytes total ÷ 16,384 pages = 528 bytes/page; 528 − 512 = 16 spare bytes/page. Two independent public sources (ps2savetools.com and the DartPower gist) both state the same 512+16=528 figure and both further break the 16 spare bytes down as 12 bytes of ECC (three bytes × four 128-byte data sub-chunks) plus 4 unused bytes. This is a three-way convergence: local arithmetic on a real file, and two independently-styled restatements of community documentation.
- **Pages per cluster / block:** `pages_per_cluster` default 2 (→ 1024-byte clusters), `pages_per_block` default 16 (an erase block is 16 pages). These are superblock fields, not hardcoded constants — a parser must read them from the card rather than assume the defaults, per §4.
- **Common capacities:** the standard/baseline real PS2 memory card is 8 MB (nominally; 8,650,752 raw bytes including spare, per the local PCSX2 evidence and the standard-layout table in §4). Larger virtual capacities (16MB/32MB/64MB/128MB) are known to be used by some emulators and homebrew loaders for user convenience (e.g. a `pcsx2-128mb-memcard` fork repository turned up directly in a GitHub search during this pass, confirming at least one real 128MB variant exists in the ecosystem) — **this was only confirmed via a repository name in a search result, not via reading that repository's source**, so treat "cards larger than 8MB exist and are used in practice" as confirmed, but do not treat any specific larger-capacity geometry (its exact `clusters_per_card`/`alloc_end` values) as confirmed by this pass.
- **Raw vs. formatted/user-visible capacity:** the superblock's own `alloc_offset` (first allocatable cluster, default 41 per §4) and `alloc_end` (end boundary, default 8135) fields mean a meaningful chunk of the nominal 8MB is reserved (superblock page, unused pages, FAT/indirect-FAT clusters, backup blocks) before user files can be stored — "raw card size" and "usable space for files" are not the same number, and any future geometry-reporting code must read these fields rather than assume total size minus a fixed constant.
- **Extensions — explicit finding, not just an instruction followed:** `.ps2` (PCSX2's own default extension, confirmed locally = raw+spare/ECC 528-byte-stride), `.mcd`, `.mc2` are commonly used by various emulators/tools for what multiple sources describe as the same raw-card layout (with or without the ECC spare bytes present — this varies by tool and was **not independently confirmed byte-for-byte for every extension** in this pass); `.vmc`/`.vm2` names appear in emulator documentation (e.g. some PS2-on-other-platforms tooling) as similarly alternate names for a raw-card dump. None of the sources read in this pass state that file extension reliably determines whether spare/ECC bytes are present — **do not assume extension determines structure** is stated here as a finding: the only reliable way to know whether a given file includes the 16-byte spare area is to check whether its total size is evenly divisible by 528 (raw+spare) versus 512 (spare-stripped) per page-count, or (more robustly) to parse the superblock's own `page_len` field once the file is confirmed to have one. This mirrors the same distinction `APOLLO_SAVE_TOOL_AUDIT.md` §3/§4 already drew for PS1 (RAW/GME/VGS/VMP container types vs. PSV single-save export) — a full raw card dump and a single-save export container are structurally unrelated formats that happen to share loose extension conventions across tools, and the PSV/PSU single-save export format exists for PS2 as well (see §11, citing that same audit's `ps2mc.h`/`psv_header_t` findings).

## 4. Superblock

**Source for this section:** the `mymc` `ps2mc.py` raw struct format string (`"<28s12sHHHHLLLLLL8x128s128sbbxx"`, little-endian, public domain per §2) was used to **reconstruct exact byte offsets independently**, then cross-checked against the ps2savetools.com/gist rendered tables. The reconstruction is shown so the offsets below are traceable rather than merely copied from a rendered table:

| Bytes | Cumulative offset | Field (per ps2savetools.com/gist naming) |
|---|---|---|
| `28s` | 0x00–0x1C | magic — `"Sony PS2 Memory Card Format"` (mymc's own constant is `"Sony PS2 Memory Card Format "` — note the **trailing space**, which `memory_card_inventory.rs`'s 30-byte/"first 30 bytes" check would need to account for if it is ever extended to check more than the current 28-29 characters) |
| `12s` | 0x1C–0x28 | version — e.g. `"1.X.0.0"`-shaped text |
| `H` | 0x28–0x2A | page_len (default 512) |
| `H` | 0x2A–0x2C | pages_per_cluster (default 2) |
| `H` | 0x2C–0x2E | pages_per_block (default 16) |
| `H` | 0x2E–0x30 | unknown/reserved halfword |
| `L` | 0x30–0x34 | clusters_per_card (default 8192) |
| `L` | 0x34–0x38 | alloc_offset (default 41) |
| `L` | 0x38–0x3C | alloc_end (default 8135) |
| `L` | 0x3C–0x40 | rootdir_cluster (default 0) |
| `L` | 0x40–0x44 | backup_block1 (default 1023) |
| `L` | 0x44–0x48 | backup_block2 (default 1022) |
| `8x` | 0x48–0x50 | padding (8 bytes, unnamed) |
| `128s` | 0x50–0xD0 | ifc_list — 32 × 4-byte indirect-FAT cluster pointers |
| `128s` | 0xD0–0x150 | bad_block_list — 32 × 4-byte defective-erase-block entries |
| `b` | 0x150 | card_flags (1 byte) |
| `b` | 0x151 | reserved (1 byte) |
| `xx` | 0x152–0x154 | padding (2 bytes) |

Summing the struct gives exactly 340 bytes (28+12+2+2+2+2+4+4+4+4+4+4+8+128+128+1+1+2), which independently **confirms** the "superblock is 340 bytes" claim from both ps2savetools.com and the gist via a completely different method (arithmetic on the actual `mymc` parser's struct string, not trusting either rendered table on its own).

**A discrepancy worth flagging, not silently resolving:** the ps2savetools.com-derived table (as rendered to this pass) lists a separate `card_type` byte at 0x150 (must equal 2) *and* `card_flags` at 0x151, i.e. two named 1-byte fields at that location. The `mymc` struct format string only shows `"bb"` (two unnamed 1-byte fields) at that same offset range, which the WebFetch summarization of `ps2mc.py` labeled "card flags" and "reserved" without giving a second name. **This document cannot independently confirm whether byte 0x150 is `card_type` (must be 2) or the first flags byte** — both public-doc renderings agree there are two meaningful bytes around offset 0x150–0x151, but their exact field identity was not reconciled with full confidence in this pass. Flag as: offset region confirmed (0x150–0x151, two bytes), exact field-to-byte mapping **not fully confirmed** — a future parser must re-verify this specific mapping against actual card bytes (e.g. real PCSX2 cards, which are known-good per §12) before relying on it, rather than trusting either rendering blindly.

Card-flags bit meanings (rendered consistently across both prose sources): `0x01` = CF_USE_ECC (card supports ECC), `0x08` = CF_BAD_BLOCK (card may contain bad blocks), `0x10` = CF_ERASE_ZEROES (erased state reads as all-zero rather than all-one).

**Sanity/bounds checks a future parser should perform (design-only, not implemented):**
- `magic` must exactly equal the known constant (accounting for the trailing-space variant noted above) — reject, don't guess, on any mismatch.
- `page_len` should be a small allowed set of known values (512 is the only value confirmed by any source in this pass) — reject or flag as `UnsupportedVariant` (matching the existing PS1/current-PS2 pattern already used in `memory_card_inventory.rs`) rather than trusting an arbitrary value.
- `pages_per_cluster` and `pages_per_block` must be small positive powers-of-two-shaped values that, multiplied by `page_len`, do not overflow a `usize` and do not imply a cluster/block larger than the whole card — reject on overflow or nonsensical magnitude, never wrap/truncate silently.
- `clusters_per_card` × (`pages_per_cluster` × `page_len`) must not exceed the actual file size being inspected (cross-check declared geometry against the real byte length on disk) — a card that claims more clusters than its file actually contains is either truncated or lying, and must be flagged, never trusted.
- `alloc_offset` and `alloc_end` must satisfy `alloc_offset <= alloc_end <= clusters_per_card`, and `rootdir_cluster` must fall within `[alloc_offset, alloc_end)` — any violation is a structural-integrity failure to report, not silently correct.
- `ifc_list` entries must each individually be a plausible cluster index (within total card clusters) before ever being dereferenced — never trust an index read from the card without a bounds check first (this is the same discipline `memory_card_inventory.rs`'s PS1 path already applies by refusing to guess on any out-of-taxonomy header byte).
- No superblock-level checksum/ECC field beyond the per-page spare-area ECC (§10) was confirmed by any source read in this pass — if one exists, it was not found; state this as **UNKNOWN**, not absent.

## 5. Allocation / FAT

**Confirmed (via `mymc`'s constants, cross-checked against ps2savetools.com/gist prose):**
- Each FAT entry is a 32-bit little-endian word. The most-significant bit (`PS2MC_FAT_ALLOCATED_BIT = 0x80000000`) marks the cluster as allocated; the low 31 bits (`PS2MC_FAT_CLUSTER_MASK = 0x7FFFFFFF`) are either the index of the next cluster in the chain, or a terminal marker. `PS2MC_FAT_CHAIN_END = 0xFFFFFFFF` marks end-of-chain for an allocated entry; `PS2MC_FAT_CHAIN_END_UNALLOC = 0x7FFFFFFF` is the equivalent unallocated/free sentinel. This closed, three-state model (allocated+next, allocated+end, free) is a clean, checkable taxonomy — matching the same "closed enum, fail-closed on anything else" discipline `memory_card_inventory.rs` already applies to PS1 block-type bytes.
- The FAT itself is accessed indirectly: the superblock's `ifc_list` (32 entries) points to indirect-FAT clusters, which in turn point to the actual FAT clusters — a two-level ("double-indirect", per the sources read) indexing scheme, described in both prose sources as: for a 1024-byte cluster holding 256 four-byte entries, `fat_offset = fat_index % 256`, `indirect_index = fat_index / 256`. Both sources describe this identically, which is reassuring, but **neither source's exact formula was independently verified against real bytes in this pass** (no FAT cluster contents were read from the local PCSX2 cards — header-only inspection was the bound for this audit, per the task's local-files constraint). Treat the two-level indirect-FAT structure as **plausible and consistently reported**, not as independently byte-verified by this document.
- ps2sdk's `libmc.h`/`mcman.h` were only confirmed at search-snippet depth (§2) — they were not read in enough depth to add or contradict anything about FAT structure specifically.

**Chain-traversal rules for a future reader (design-only):**
- Maximum safe chain length is bounded by `clusters_per_card` (a chain can never legitimately be longer than the total number of clusters on the card) — this is a coarse but always-available bound, not a universal constant, since card capacity varies (§3).
- **Explicit cycle-detection requirement:** any FAT-chain walk must maintain a visited-cluster set (or bitset sized to `clusters_per_card`) and either (a) abort with a structural-integrity warning the moment a previously-visited cluster is seen again, or (b) enforce a hard iteration cap equal to `clusters_per_card` and abort if exceeded — never trust the `0xFFFFFFFF` end-marker alone to terminate a walk, since a malformed or adversarial card could construct a cycle that never presents that marker.
- Every cluster index read from a FAT entry must be bounds-checked against `[alloc_offset, alloc_end)` (or at minimum `[0, clusters_per_card)`) before being used to seek into the file — an out-of-range index is a structural failure to report, never an index to clamp or wrap.

## 6. Directory entries

**Confirmed via `mymc`'s `ps2mc_dir.py` struct format string** (`"<HHL8sLL8sL28x448s"`, little-endian), reconstructed byte-by-byte:

| Bytes | Offset | Field |
|---|---|---|
| `H` | 0x00–0x02 | mode (type/permission flags, see `DF_*` below) |
| `H` | 0x02–0x04 | unknown/reserved halfword |
| `L` | 0x04–0x08 | length (file size in bytes, or entry count for a directory) |
| `8s` | 0x08–0x10 | created timestamp |
| `L` | 0x10–0x14 | fat_cluster (first cluster of the entry's data chain; `0xFFFFFFFF` for an empty file per the prose sources) |
| `L` | 0x14–0x18 | parent_entry (used by `.`/`..`-equivalent entries to reference the parent) |
| `8s` | 0x18–0x20 | modified timestamp |
| `L` | 0x20–0x24 | attr (user-defined attribute, meaning not further documented in any source read) |
| `28x` | 0x24–0x40 | padding (28 bytes, unnamed) |
| `448s` | 0x40–0x200 | name |

Total: 512 bytes, matching every source's "512-byte directory entry" claim.

**A discrepancy worth flagging explicitly:** the ps2savetools.com/gist prose renderings both describe the name field as `byte[32]` at offset 0x40 ("32-byte, zero-terminated filename"), while the actual `mymc` struct format string allocates **448 bytes** at that offset (0x40 through 0x200, the end of the 512-byte record). These are not necessarily in conflict — PS2 save filenames are conventionally short (well under 32 characters) and a zero-terminated string inside a 448-byte buffer would look identical to one inside a 32-byte buffer for any real short name — but this document cannot confirm from the sources read whether (a) only the first 32 bytes of that 448-byte span are meaningful and the rest is genuinely reserved/padding that the prose sources chose not to mention, or (b) the prose sources' "32 bytes" figure is simply wrong/oversimplified and the real usable name field is longer. **Stated as unresolved rather than guessed** — a future parser should read the full 448-byte span, treat it as null-terminated, and not assume a 32-byte hard cap without separate verification.

Entries per cluster: with a 1024-byte default cluster (§3/§4) and a 512-byte directory entry, that is exactly 2 entries per cluster at the default geometry — but this is a derived figure specific to the default `pages_per_cluster`/`page_len` values, not a fixed constant; a parser must compute it from the superblock's actual geometry fields, never hardcode it.

**Mode (`DF_*`) flags**, confirmed via `mymc`'s constants: `0x0001` READ, `0x0002` WRITE, `0x0004` EXECUTE, `0x0008` PROTECTED, `0x0010` FILE, `0x0020` DIR, `0x0040` (an internal "create directory" transient flag per the constant name `DF_O_DCREAT`, unlikely to appear in an on-disk entry), `0x0200` (`DF_O_CREAT`, likely also a transient open-flag rather than an on-disk state), `0x0800` POCKETSTN (PocketStation save), `0x1000` PSX (a PS1 save stored via the PS2's card, i.e. the PS2 filesystem can itself hold PS1-format saves as a special entry type — a fact worth future cross-reference against `memory_card_inventory.rs`'s existing PS1 path, though this audit did not investigate that interaction further), `0x2000` HIDDEN, `0x8000` EXISTS (entry-in-use marker). Two of these (`0x0040`/`0x0200`) are named in a way that suggests they are open-mode flags reused from a POSIX-like API rather than meaningful on-disk directory-entry state — **flagged as uncertain, not asserted**, since neither prose source discusses this distinction and it was inferred from the constant names alone.

**Timestamp format** (8 bytes), consistent across both prose sources: offset 0x01 second, 0x02 minute, 0x03 hour, 0x04 day-of-month, 0x05 month, 0x06 (2 bytes) four-digit year (byte 0x00 is unaccounted for in the rendered tables — likely a reserved/unused leading byte, not independently confirmed). Both sources state all timestamps use Japan Standard Time (UTC+9) regardless of the console's configured timezone — a detail a future reader must apply consistently (convert to UTC using a fixed +9 offset, never trust a host-local-time assumption).

**`.`/`..` convention:** the `parent_entry` field is described as being used by "dot entries" (i.e. a directory's own self-referencing/parent-referencing pseudo-entries analogous to `.`/`..` in POSIX filesystems) to record the parent directory's entry index — consistent with both prose sources, not independently verified against real bytes in this pass.

**Deleted/unlinked entry semantics:** neither prose source, nor the `mymc` constants list, described an explicit "this entry was deleted" bit distinct from the `EXISTS` flag being clear — the working assumption (not independently confirmed) is that `DF_EXISTS` clear is how the PS2 filesystem marks a free/unused directory-entry slot, analogous to PS1's `0xA1`-family deleted markers but expressed as a single flag bit rather than a separate byte value. Flagged as **plausible, not confirmed** — a future parser must not assume an entry with `DF_EXISTS` clear is safe to reuse without also independently checking its FAT chain isn't still referenced elsewhere (mirrors the same caution `memory_card_inventory.rs`'s PS1 path already exercises around deleted-vs-corrupted distinction).

## 7. Directory traversal safety (design-only)

A future bounded, read-only PS2 directory/FAT reader should apply the following — none of this is implemented anywhere in this repository:

- **Cycle detection, directories:** maintain a visited-cluster set across the whole directory tree walk (not just per-directory), sized against `clusters_per_card`; refuse to descend into a directory whose starting cluster has already been visited, and report it as a structural anomaly rather than looping forever.
- **Cycle detection, FAT chains:** as described in §5 — visited-set or hard iteration cap, never trust the end-marker alone.
- **Invalid-cluster-number rejection:** every cluster index read from a directory entry (`fat_cluster`) or a FAT entry must be bounds-checked against the card's actual allocatable range *before* it is ever used to seek/read — an out-of-range index must be reported and the entry treated as unreadable, never silently clamped into range (clamping would corrupt the evidence, not just fail safely).
- **Size-field sanity caps:** a directory entry's declared `length` should be sanity-checked against remaining card capacity (a file cannot legitimately be larger than the whole card, and in practice should be far smaller) — an implausibly large declared size is a structural-integrity flag, not a value to trust for any subsequent allocation or buffer sizing.
- **Malformed entry-count handling:** a directory's own `length` field (entry count, per §6) must similarly be bounds-checked before being used to size a loop or allocation — reject/flag rather than trusting a card-supplied count to drive iteration without an independent cap.
- **Invalid-timestamp handling:** reject or flag (never crash-parse) a timestamp whose fields fall outside their documented ranges (e.g. month outside 1–12, hour outside 0–23) — construct a best-effort "raw bytes observed, could not interpret as a valid timestamp" evidence entry rather than panicking or silently substituting a default.
- **Invalid-encoding handling:** filename bytes must be lossy-decoded (e.g. via a replacement-character strategy) with an attached warning when they are not valid text in the expected encoding, never panic on invalid bytes.
- **Nesting-depth cap:** enforce a maximum directory-nesting depth (a small fixed number, since real PS2 save directories are known from every source read to be shallow — one save-folder level under the root, per §8) and refuse to descend further, reporting the anomaly, rather than assuming card-supplied nesting is bounded by good faith alone.
- **Duplicate / case-equivalent name handling:** report duplicate or case-equivalent directory-entry names as an anomaly; never silently deduplicate or pick a "winner" between them, since doing so would discard evidence about a card's actual (possibly corrupted or hand-edited) state.
- **Names must never be used directly as host filesystem path components.** Any on-card filename must be treated as opaque/untrusted data — sanitized or replaced with an internally-generated opaque index before ever touching a host path, exactly the same discipline this repository's own `crates/archivefs-core/src/safe_read/` module already applies to its trusted-root path handling elsewhere in the codebase (confirmed present at that path in this worktree; module internals were not re-read in this pass beyond confirming its existence as the parallel to cite — this audit did not re-audit `safe_read`'s own implementation).

## 8. Save / game identity

PS2 (and PS1) share Sony's regional catalog-numbering convention. Per the WebSearch results in §2 (ConsoleMods wiki and forum-thread summaries, search-snippet depth) and cross-checked against `APOLLO_SAVE_TOOL_AUDIT.md`'s own PS1 findings (`ps1card.c loadRegion()`: header bytes 10–11 as ASCII `"BA"`=America, `"BE"`=Europe, `"BI"`=Japan — a real, source-confirmed enum for PS1):

- **Region-prefix convention:** `BA` = America, `BE` = Europe, `BI` = Japan (and a `BC` = China prefix also appeared in one search snippet, not further corroborated). This matches PS1's own two-letter region convention exactly, consistent with both platforms sharing Sony's regional catalog-numbering scheme.
- **Catalog-number infix:** the well-known `SLUS`/`SLES`/`SLPM`/`SCUS`/`SCES`/`SCAJ`-style infixes (Sony's own first-party/licensed catalog prefixes, `S`=Sony-published-or-licensed convention, `L`/`C` and the following two letters distinguishing licensee-vs-first-party and region in ways this document did not fully re-derive from primary sources) are the same catalog-number system used across PS1/PS2/PS3, per the search-snippet evidence — this is **consistent with, not independently re-derived beyond**, what `APOLLO_SAVE_TOOL_AUDIT.md` already established for PS1's `saveProdCode`.
- **Full save-directory name shape** (per the task brief's own examples, corroborated by the search snippets): `<region-prefix>-<catalog-number>`, e.g. `BASLUS-20312`, `BESLES-12345`, `BISLPM-xxxxx` — a directory name matching this shape (correct region-prefix letter pair, followed by a hyphen, followed by a plausible catalog-number pattern) is exactly the class of structured-but-not-self-certifying evidence `APOLLO_SAVE_TOOL_AUDIT.md`'s own evidence matrix (§6 there) already classifies PS1 product codes as: **SUPPORTING evidence**, promotable to **CONFIRMED** only against an actual DAT/catalogue of known product codes — never CONFIRMED from pattern-matching alone, since a folder can be renamed by hand or by a buggy tool.
- **`icon.sys` display title alone** (a human-facing text field, see §9): **HEURISTIC** at best — same tier this repo's own house style already assigns PS1 save-title text in the Apollo audit's evidence matrix.
- **`BADATA-SYSTEM`-style directories:** these must be explicitly flagged as **not a normal game save** — they hold system/BIOS configuration data, not a game's save state, and a directory-name matcher must special-case and exclude this pattern rather than ever misclassifying it as a game-identity candidate. (This convention was named in the task brief itself; this document did not independently re-verify the exact literal string `BADATA-SYSTEM` against a primary PS2 source in this pass, but the general principle — that the PS2 memory card root can contain non-game housekeeping directories that must never be treated as save-identity evidence — is consistent with every source describing the root directory as a general-purpose directory rather than an exclusively-game-saves directory.)

**Classification summary for this section** (using this document's defined vocabulary):
| Evidence | Tier |
|---|---|
| Directory name matches `<region>-<catalog>` shape only | SUPPORTING |
| Directory name matches AND cross-checked against a known product-code catalogue/DAT | CONFIRMED |
| `icon.sys` display title/subtitle text alone | HEURISTIC |
| `BADATA-SYSTEM` (or similarly named system directories) | UNKNOWN as game identity — explicitly excluded, not merely low-confidence |

## 9. `icon.sys` / metadata

`APOLLO_SAVE_TOOL_AUDIT.md` §4 already documents real struct-level detail extracted from Apollo's `ps2mc.h` (a header file, GPLv3-licensed project, concepts cited not code copied — see that document's own §13 licensing note): `ps2_IconSys_t` contains background-gradient colors (4 corners), 3 light directions/colors, an ambient-light value, a **null-terminated 68-byte Shift-JIS title field**, and icon/copy-icon/delete-icon **filenames** (64 bytes each, referencing separate files inside the save rather than embedding icon data directly in `icon.sys`). This audit did not find additional public-source detail beyond what that existing document already captured, and treats it as the authoritative citation for `icon.sys`'s field layout rather than re-deriving it.

**Assessment — can display title/subtitle be safely exposed as read-only text without any image decompression?** Yes, and this is worth stating clearly: the title/subtitle text fields in `icon.sys` are plain fixed-offset Shift-JIS text, structurally independent of the icon files it references by name. Decompression/mesh-parsing is only needed to render the actual 3D icon model (a separate referenced file, per the filename fields above) — that is not required for a text-only inventory display. A future PS2 inventory reader could therefore expose `icon.sys` title text as read-only evidence (classified HEURISTIC per §8) without ever touching icon-mesh decompression, which is a meaningfully larger and riskier piece of format-specific parsing that this document does not recommend attempting in a first pass.

## 10. ECC / spare data

The 512-byte data area of each page is described (consistently across both prose sources read in §2) as divided into four 128-byte chunks, each of which gets a 20-bit Hamming code computed and stored as 3 ECC bytes in the page's 16-byte spare area (4 chunks × 3 bytes = 12 ECC bytes; the remaining 4 spare bytes are unused). This 12-of-16 figure is corroborated by the WebSearch-snippet claim about PCSX2's own page layout (§2), giving two independently-styled sources in agreement, though neither PCSX2's actual source file nor a primary NAND/Hamming-code specification was read directly in this pass.

**What was NOT confirmed:** the exact bit-level Hamming-code construction (which bits map to which parity groups, the precise algorithm for computing "column parity"/"line parity" as named in the sources) was only described at a summary level by the WebFetch tool's rendering of the source pages, not read as raw formula/pseudocode. **Treat the exact ECC algorithm as UNKNOWN / not independently confirmed** by this pass — the byte-count breakdown (12 ECC + 4 unused, per 16-byte spare) is reasonably well corroborated; the bit-level Hamming construction is not.

**Explicit statement for any future implementation:** a future PS2 inventory reader must never rewrite or repair ECC/spare bytes — at most, it may optionally verify a page's stored ECC against a recomputed value and report a mismatch as a health warning (the same "detect and report, never silently fix" posture `memory_card_inventory.rs`'s PS1 path already applies to its XOR checksum). Even that verification step requires confirming the exact algorithm first (currently UNKNOWN per above) — until then, no ECC verification should be attempted at all, only presence/absence of a spare area (528 vs. 512-byte-stride) as a structural fact.

## 14. Implementation decision

**Decision: partial-A.** Specifically: **A for geometry/superblock recognition only; B for directory/FAT/save-entry enumeration.**

Reasoning, stated plainly against what this pass actually managed to confirm:

- The core raw-card geometry (528-byte page stride = 512 data + 16 spare) is confirmed by three independent lines of evidence converging: real local arithmetic on genuine PCSX2-generated files (§3/§12), and two independently-styled public documentation renderings (§2) — this is a strong basis for **A** on geometry recognition specifically.
- The superblock's field layout and exact byte offsets were independently reconstructed from `mymc`'s actual public-domain struct format string (§4), not merely trusted from a rendered table — and that reconstruction's total (340 bytes) matches both prose sources' claimed superblock size exactly. This is also a reasonably strong basis for **A** on superblock-field recognition, **with one explicitly unresolved discrepancy** (the `card_type`/`card_flags` byte-identity question at offset 0x150–0x151, §4) that a real implementation would need to resolve against actual card bytes before trusting that specific field.
- By contrast, the FAT indirect-indexing formula (§5) and the directory-entry name-field-length discrepancy (32 bytes claimed by prose sources vs. 448 bytes allocated by `mymc`'s actual struct, §6) were **not** independently verified against real card bytes in this pass — no FAT or directory cluster contents were read from the local PCSX2 files (header-only was the bound for this audit). These are exactly the fields a directory/FAT enumerator would need to trust with confidence, and this pass cannot honestly claim that confidence yet.

**What this means concretely:** a Phase 2 that reads the superblock, validates its fields against the sanity checks in §4, and reports card geometry (page size, cluster size, capacity, usable-vs-reserved space) as structural evidence — without ever walking the FAT or enumerating directory entries — is well-supported by the evidence in this document (**A**). A Phase 2 that walks FAT chains or lists directory entries is **not yet well-supported** (**B**) until the FAT double-indirect-indexing formula and the directory-entry name-field question are independently verified against real card bytes (ideally the local PCSX2 cards already on this host, or a freshly-generated empty PCSX2 card per §13) rather than trusted from prose-rendered documentation alone.

## 15. Future implementation plan — "PS2 MEMORY CARD INVENTORY PHASE 2" (geometry/superblock slice only, per §14's partial-A)

Scoped narrowly to what §14 actually supports:

- **In scope for a first Phase 2 slice:** parse the superblock (§4 field layout), apply all the sanity/bounds checks listed there, and report structural evidence — page size, cluster size, pages-per-block, total/allocatable capacity, backup-block presence, card-flags bits (with the 0x150/0x151 ambiguity either resolved by then or explicitly surfaced as "flags byte identity uncertain" in the report itself rather than asserted) — as a richer `MemoryCardInventory` for the `Ps2` format variant, still with `entries: Vec::new()` and `health` reflecting whatever the sanity checks find (still no directory/save enumeration).
- **Deferred until FAT/directory evidence is independently verified (per §14's B half):** bounded directory enumeration, per-file/save summaries, game-serial evidence extraction from directory names (§8), `icon.sys` title exposure (§9), timestamps/sizes from directory entries — all of this needs the FAT-chain and directory-entry-layout questions closed first, ideally against real bytes from the local PCSX2 cards or a fresh PCSX2-generated empty card (§13).
- **Explicitly still NOT in scope, at any phase, per this task's own constraints:** extraction, injection, deletion, repair, formatting, resigning, per-save restore, or any snapshot/restore redesign. Even once directory/FAT enumeration evidence is solid enough for a future "B→A" reassessment, the module's existing design principle (shared-container, read-only, never decompose or repair) should continue to hold — enumeration is additive evidence on top of the existing whole-card-is-the-unit model, not a step toward per-save extraction.
- GUI read-only presentation of whatever a future Phase 2 produces (geometry summary now; directory/save summaries later, once B is closed) is a reasonable eventual consumer, but wiring `memory_card_inventory` into any GUI page or CLI command is itself still not done (§1) and out of scope for this research pass.
