# Apollo Save Tool Ecosystem Audit — EmuWiz (RESEARCH ONLY)

> **Research snapshot** — This audit records findings from public GitHub repositories at the time it was written. It proposes no code, and no production Rust file in this repository was modified while producing it. It does not implement, sketch, or scaffold Save Vault card parsing, restore, save-patch execution, or community-save downloading. Save Vault implementation code and Publisher Profiles code were not read or touched.

**Scope:** `bucanero/apollo-ps4`, `bucanero/apollo-lib`, `bucanero/apollo-saves` — concepts, formats, and safety rules reusable for EmuWiz's Save Vault feature area (phase 1 discovery, phase 2 snapshots/history, phase 3 restore planning), evaluated against the existing `SHARED_MEMORY_CONTAINER` design principle (a memory-card-like blob holding multiple saves is snapshotted as one atomic unit, never decomposed).
**Branch:** `feature/archivefs-unified-platform`
**Method:** GitHub REST API tree/commit inspection + direct `raw.githubusercontent.com` fetches of real source files (not code search UI, which was not reachable in this environment). No Apollo code was copied into EmuWiz. No card parser, resigner, patch engine, or downloader was written.

---

## 1. Purpose and scope

Save Vault needs domain knowledge about console memory-card and save-file formats it does not yet implement. Apollo Save Tool is the most mature open-source project in this space (PS1/PS2/PS3/PS4/PS5 save management, memory-card editing, save-patch codes, and a community save database). This document extracts *concepts and format knowledge* — byte offsets, identity primitives, safety hazards — from the real Apollo source, and maps them onto what EmuWiz would need for Save Vault, without proposing that EmuWiz adopt Apollo's riskier behaviors (arbitrary patch-script execution, cross-account resigning, or save downloading) wholesale.

Nothing in this document is a design decision for Save Vault; it is raw material and a risk classification for whoever makes that decision next.

## 3. PS1 memory card findings

**Source:** `apollo-ps4/include/ps1card.h` (full), `apollo-ps4/source/ps1card.c` (targeted read).

Apollo's PS1 card model (`ps1mcData_t`, `ps1card.h:39-53`) is a flat, 15-slot array (`PS1CARD_MAX_SLOTS = 15`), each slot backed by a 128-byte header block (`PS1CARD_HEADER_SIZE`) plus an 8192-byte data block (`PS1CARD_BLOCK_SIZE`); total raw card size `PS1CARD_SIZE = 131072` bytes (128 KB), matching the physical PS1 memory card.

| Primitive | Location | Detail |
|---|---|---|
| Container formats recognized | `ps1card.h:8-16` (`enum ps1card_type`) | `RAW` (.mcr/.mcd/.bin/.srm), `GME` (DexDrive), `VGS` (bleem!/Virtual Game Station), `VMP` (PS3 Virtual Memory Card Adaptor), `MCX` |
| Per-save container formats | `ps1card.h:18-25` (`enum ps1save_type`) | `AR` (Action Replay), `MCS` (raw single-save), `RAW`, `PSV` (PS3 signed export) |
| Block/slot type & corruption marker | `ps1card.c` `loadSlotTypes()` (~line 389) | First header byte per 128-byte block: `0xA0` formatted, `0x51` initial, `0x52` middle-link, `0x53` end-link, `0xA1`/`0xA2`/`0xA3` deleted variants; **any other byte value is classified `PS1BLOCK_CORRUPTED`** (`ps1card.h:27-37`, `enum ps1block_type`) — an explicit fail-closed corruption marker keyed to one byte, not a heuristic |
| Region evidence | `ps1card.c` `loadRegion()` (~line 264) | 16-bit value read from header bytes 10-11: ASCII `"BA"` = America, `"BE"` = Europe, `"BI"` = Japan (comment at `ps1card.h:47`) — a small closed enum, not a free-text field |
| Product/title-code identity | `ps1card.c` `loadStringData()` (~line 431) | `saveProdCode` = header bytes 12-21 (10 bytes, e.g. `BASLUS-00067`-style code minus region prefix already split out); `saveIdentifier` = header bytes 22-29 (8 bytes) |
| Save filename | same function | `saveName` = header bytes 10-29 (20 bytes, includes region+prodcode+identifier concatenated as the on-card filename) |
| Icon/title metadata | `ps1mcData_t` fields, `ps1card.h:43-52` | `iconPalette[16]` (16-color CLUT), `iconData[3][256]` (three 16×16px icon frames), `iconFrames` (animation frame count), `saveTitle[65]` — 64 bytes of **Shift-JIS** text copied from the *data* block (not the header) at offset 4 |
| Corruption/checksum repair | `ps1card.c` `calculateXOR()` (~line 246) | XOR of the first 126 header bytes stored at header byte 127 — Apollo **recomputes and overwrites** this checksum on save/export (`fixData` parameter threaded through `openMemoryCard`/`saveMemoryCard`), i.e. it actively repairs card headers rather than only reporting corruption |
| Import/export transforms | `ps1card.h:55-92` | `openMemoryCard`/`openMemoryCardStream` (any of the container types above → internal model), `saveMemoryCard`/`saveMemoryCardStream` (internal model → chosen container type, with `fixData` repair option), `openSingleSave`/`saveSingleSave` (per-save AR/MCS/PSV extraction), `getSaveBytes`/`setIconBytes`/`toggleDeleteSave`/`formatSave` |
| PSV (signed single-save) naming | `ps1card.c` (~line 775) | Constructs `PSV` export filenames from region + product code + identifier, confirming those three fields are treated as the *canonical identity key* for a single save |

**Key structural fact for EmuWiz:** a PS1 card is a fixed 15-entry table of independently typed/identified blocks; each entry carries its own region+product-code+identifier (game-level identity) and its own corruption marker — but Apollo still treats the **card image** as the unit that is opened/exported/repaired, and only *optionally* extracts one slot at a time via a separate single-save path. The multi-slot table itself is never torn apart implicitly.

## 4. PS2 VMC (Virtual Memory Card) findings

**Source:** `apollo-ps4/include/ps2mc.h` (full), `apollo-ps4/include/mcio.h` (full, PS3-MCA-derived), tree listing of `source/ps2icon.c`, `source/psv_ps2.c`, `source/psv_resign.c` (targeted read for PSV/PS2 resigning, see §5-adjacent crypto below).

PS2 VMC handling in Apollo is split across two layers:

- **`mcio.h`/`mcio.c`** — a low-level PS2 memory-card filesystem driver, directly derived from the `ps3mca-tool` project (attribution comment at `mcio.h:1-18`, itself GPLv3). It exposes a POSIX-like API: `mcio_mcOpen/mcClose/mcRead/mcWrite/mcSeek`, `mcio_mcDopen/mcDclose/mcDread` (directory enumeration via `struct io_dirent`), `mcio_mcFormat/mcUnformat`, `mcio_mcCreateCrossLinkedFile`, and page-level `mcio_mcReadPage(pagenum, buf, ecc)` — i.e. **ECC is handled per-page**, not per-file, matching the real PS2 memory-card hardware's ECC-per-512-byte-page layout. Error codes (`sceMcResFailReadCluster`, `sceMcResFailCheckBackupBlocks`, `sceMcResFailAuth`, etc., `mcio.h:90-111`) distinguish authentication failures, format failures, and cluster/backup-block corruption as separate typed conditions rather than one generic "bad card" error.
- **`ps2mc.h`** — file-format structures for **individual exported PS2 saves**, sourced (per its own header comment) from the PSV-Exporter and CheatDevicePS2 projects:
  - `McFsEntry` (512 bytes) — PS2 memory-card filesystem directory entry: `mode`, `length`, `created`/`modified` (`sceMcStDateTime`, packed BCD-like date/time), `cluster`, `dir_entry`, `attr`, 32-byte `name`.
  - `psv_header_t` — the container wrapper for a signed single-save export (`magic = "\x00VSP"`, a 20-byte `salt`, a 20-byte `signature`, `headerSize` (0x2C for PS2, 0x14 for PS1), `saveType` (1=PS1, 2=PS2)) — **the same PSV container format is shared between PS1 and PS2 single-save exports**, distinguished only by `saveType` and `headerSize`.
  - `ps2_header_t` / `ps2_MainDirInfo_t` / `ps2_FileInfo_t` — the PSV payload's internal table of contents: an `icon.sys` position/size plus up to three icon positions/sizes, a file count, then per-file directory entries (name, size, attribute, created/modified, byte offset).
  - `ps2_IconSys_t` — the PS2 `icon.sys` metadata block: background gradient colors (4 corners), 3 light directions/colors, ambient light, a null-terminated **Shift-JIS title** (68 bytes), and icon/copy-icon/delete-icon filenames (64 bytes each) — this is the PS2 equivalent of PS1's icon+title metadata, but stored as a *named file inside the save* rather than a fixed header field.
  - `maxHeader_t`/`maxEntry_t` (MAX format) and `cbsHeader_t`/`cbsEntry_t` (CBS/CodeBreaker format) and `xpsEntry_t` — three additional **compressed** PS2 save-archive formats (MAX uses LZARI compression per `apollo-ps4/source/lzari.c`; CBS carries its own `decompressedSize`/`compressedSize` pair), each with its own name/title/date metadata duplicated in a format-specific header.

**Identity and provenance implications:** PS2 save identity is *file-level*, not card-level — a save is identified by its containing directory name (matching a PS2 title's canonical save-folder name, e.g. `BASLUS-20312` style) plus the `icon.sys` title text, not by any single fixed byte offset the way PS1's header is. Corruption detection for PS2 is delegated to the low-level ECC/cluster-check machinery in `mcio.c` (page ECC, backup-block validation) rather than a single checksum byte as in PS1.

**Depth caveat:** `mcio.c`/`ps2icon.c`/`psv_ps2.c` bodies were not opened in this pass (tree-listed only); the header/struct analysis above is solid (full header files read), but the exact directory-walk algorithm and ECC computation formula were not verified against the `.c` implementation.

## 5. PS4 account/user binding findings (research only — not implementing)

**This section is research only. EmuWiz does not have PS4 emulation or save-management scope today, and this audit does not propose adding it.** It is included because the *binding mechanism* — how a save is cryptographically or structurally tied to one account — is the clearest illustration of cross-account restoration risk, which is directly relevant to how cautious Save Vault's restore-planning phase (phase 3) should be even for non-PS4 platforms with weaker binding.

**Source:** `apollo-ps4/include/sfo.h` (full), targeted grep of `apollo-ps4/source/saves.c` (2405 lines, not read end-to-end).

- Every PS4 save's `param.sfo` carries an `ACCOUNT_ID` parameter (8 bytes, `SFO_ACCOUNT_ID_SIZE`) and Apollo's own save index further stores `user_id`, `account_id`, and `faked_owner` per save in a local SQLite table (`saves.c` SQL: `INSERT INTO savedata(title_id, dir_name, main_title, sub_title, detail, ..., account_id, user_id, faked_owner, ...)`, confirmed via grep at `saves.c:120-122`).
- Ownership is determined purely by comparing the **locally active console's** `apollo_config.account_id` against the save's stored `account_id` (`saves.c:1462`, `:1547`, `:1594`: `apollo_config.account_id == *int_data` / `== (uint64_t)sqlite3_column_int64(res, 4)`), setting a `SAVE_FLAG_OWNER` bit. There is no cryptographic proof of possession beyond this stored 64-bit ID comparison plus whatever the console's own OS/SFO validation enforces at load time.
- `sfo_patch_t` (`sfo.h:22-28`) is the struct Apollo uses to **rewrite** a save's SFO in place: `flags` (includes `SFO_PATCH_FLAG_REMOVE_COPY_PROTECTION`), `user_id`, `account_id`, `psid` (16-byte PS4 console/profile identifier), and `directory` (the save's on-disk directory name) are all fields that get **overwritten during resigning** — i.e. resigning a PS4 save means rewriting exactly these four identity fields plus the copy-protection flag, then presumably re-running whatever integrity check the PS4 OS performs at load (not shown in the header; the actual signing/HMAC step, if any beyond SFO field patching, lives in code not inspected here).
- README claims (not independently source-verified beyond the SFO/DB findings above): the tool can "create fake Account IDs and generate offline PS4 activations," and downloaded community saves from the online database "must be resigned using Apollo before loading them in your games" — both statements are consistent with the SFO-field-patching mechanism found in source, but the activation/offline-license code path itself was not opened.

**Cross-account restoration risk, in concrete terms:** because ownership is a plain stored-ID comparison and resigning is "patch four SFO fields," a save exported from Account A can be made to load under Account B by rewriting `ACCOUNT_ID`/`user_id`/`psid`/`directory` — there is no per-console secret-bound cryptographic signature that Apollo itself cannot also produce. This is a deliberate, documented feature of Apollo (save portability across accounts/consoles), but it is exactly the class of operation Save Vault must not silently enable: rewriting identity-binding fields to make a snapshot "restoreable" under a different profile is a decision with real support/legal/trust consequences, and EmuWiz should treat any such capability (if ever proposed for any platform) as requiring explicit, unambiguous user intent — never an automatic step of a restore-planning flow.

## 6. Save identity evidence matrix

Classification follows the repo's own evidence-strength vocabulary (`CONFIRMED_IDENTITY` / `SUPPORTING_EVIDENCE` / `HEURISTIC_ONLY` / `DO_NOT_ADOPT`), applied to each primitive actually found in Apollo source above — not to Apollo's own trust decisions, which are looser than EmuWiz's house style (see §2 fail-closed discipline in `game_identity.rs`).

| Primitive | Source | Classification | Rationale |
|---|---|---|---|
| PS1 header byte 0 (block-type enum incl. `CORRUPTED`) | `ps1card.c loadSlotTypes()` | **CONFIRMED_IDENTITY** (for block *state*, not game identity) | One byte, closed enum, fail-closed default (unknown byte → corrupted) — exactly EmuWiz's own "explicit taxonomy, not guessed" pattern |
| PS1 region (header bytes 10-11, `"BA"/"BE"/"BI"`) | `ps1card.c loadRegion()` | **SUPPORTING_EVIDENCE** | Distinctive closed enum, but region alone never proves title — matches how EmuWiz already treats region bytes elsewhere (corroboration, not identity) |
| PS1 product code + identifier (header bytes 12-29) | `ps1card.c loadStringData()` | **SUPPORTING_EVIDENCE**, promotable to **CONFIRMED_IDENTITY** only when matched against a DAT/catalogue of known product codes (same rule EmuWiz already applies to disk boot-sector evidence) | Structured, bytes-derived, but a free-ish string field with no cross-check in Apollo itself |
| PS1 XOR header checksum (byte 127) | `ps1card.c calculateXOR()` | **DO_NOT_ADOPT as identity; SUPPORTING_EVIDENCE as integrity-only** | It is a corruption/repair mechanism, not identity — and Apollo's own posture of *silently recomputing and overwriting* it on every export is explicitly the wrong default for a preservation tool (see §7) |
| PS1 icon/title (Shift-JIS, data block offset 4) | `ps1card.c loadStringData()` | **SUPPORTING_EVIDENCE** | Human-facing provenance, same tier as WHDLoad slave `name`/Amiga volume labels in EmuWiz's existing audits — never identity by itself |
| PS2 `icon.sys` title (Shift-JIS) | `ps2mc.h ps2_IconSys_t` | **SUPPORTING_EVIDENCE** | Same reasoning as PS1 title text |
| PS2 save-folder name (matches title's canonical save-dir convention) | `ps2mc.h` container structs / PS2 title conventions | **SUPPORTING_EVIDENCE**, promotable with a DAT/catalogue of canonical save-folder-name-to-title mappings | Structured but not self-certifying; a folder can be renamed |
| PS4 `ACCOUNT_ID`/`user_id`/`psid` (SFO fields) | `sfo.h sfo_patch_t` | **HEURISTIC_ONLY for "this save belongs to me,"** never **CONFIRMED_IDENTITY** for restore authorization | It is a plain stored-value comparison the tool itself can rewrite — proves nothing cryptographically; see §5 |
| PS2 ECC/cluster/backup-block validity (`mcio.h` error codes) | `mcio.h` | **CONFIRMED_IDENTITY** (for *card structural integrity*, not game identity) | Hardware-defined, closed-form validation with typed failure modes — directly analogous to EmuWiz's own container-validation-before-trust discipline |
| Apollo's own online-DB save/game folder naming (`TITLE-ID/NNNNNNNN.zip`) | `apollo-saves` tree listing | **HEURISTIC_ONLY** | Community-maintained naming convention with no cryptographic tie to the actual save bytes; useful as a *lookup key*, never as proof the contents are genuine or safe |
| Per-title custom encryption functions (`apollo_crypt_diablo3`, `apollo_crypt_silent_hill3`, etc.) | `apollo.h` | **N/A (not an identity primitive)** — but classified here because it is tempting to conflate "this save decrypts with title X's key" with identity | **HEURISTIC_ONLY** at best: a save that fails to decrypt under a guessed title-specific cipher is not proven to be a different title; it may simply be a different format version |

## 7. Checksum / encryption / compression findings

**Source:** `apollo-lib/include/apollo.h` function catalogue (full read of the declaration list), `apollo-lib/README.md` (feature claims).

Apollo's `apollo_hash_*`/`apollo_crypt_*` catalogue splits cleanly into three tiers, and the split itself is the reusable lesson:

1. **Generic, safe-to-generalize primitives** (present as declared functions in `apollo.h`): `apollo_crypt_aes_ecb`/`aes_cbc`/`aes_ctr`, `apollo_crypt_des3_ecb`/`des3_cbc`, `apollo_crypt_blowfish_ecb`/`blowfish_cbc`, `apollo_crypt_camellia_ecb`; generic hashes `apollo_hash_crc16`/`crc32`/`crc64` (each parameterized by a `custom_crc_t` polynomial config — CRC variants are configuration, not new algorithms), `apollo_hash_md5_xor`, `apollo_hash_sha1_xor64`, `apollo_hash_pbkdf2_sha1`/`pbkdf2_sha256`, `apollo_hash_adler16`, `apollo_hash_fletcher16`/`fletcher32`, `apollo_hash_murmur3_32`, `apollo_hash_djb2`/`sdbm`/`fnv1`. These are textbook algorithms; reimplementing (not copying) any of them from public specifications carries no GPL obligation and no game-specific fragility.
2. **Game-specific, brittle, not safe to generalize:** a long tail of per-title functions — `apollo_crypt_diablo3`, `apollo_crypt_silent_hill3`, `apollo_crypt_nfs_undercover`, `apollo_crypt_final_fantasy13`, `apollo_crypt_borderlands3`, `apollo_crypt_monster_hunter`, `apollo_crypt_mgs`/`mgs_base64`/`mgs_pw`, `apollo_crypt_mgs5_tpp`, `apollo_crypt_dw8xl`, `apollo_crypt_rgg_studio`, and matching per-title hashes `apollo_hash_mgspw`, `apollo_hash_ff13`, `apollo_hash_deadrising`, `apollo_hash_dbzxv2`, `apollo_hash_ffx`, `apollo_hash_kh25`, `apollo_hash_khcom`, `apollo_hash_tiara2`, `apollo_hash_castlevania`, `apollo_hash_toz`, `apollo_hash_mgs2`, `apollo_hash_sw4`. Each exists because one specific game shipped a bespoke transform, discovered by reverse-engineering that one game. This is exactly the kind of knowledge that does not generalize and should never be treated as a template EmuWiz tries to "cover the space" of — it is an open-ended, per-title reverse-engineering tax, not a format.
3. **Compression:** `apollo-lib/source/offzip.c`/`packzip.c` (not opened — presence and role only confirmed via tree listing + Makefile references) plus PS2 save-specific LZARI (`apollo-ps4/source/lzari.c`, PS2 MAX-format saves per `ps2mc.h maxHeader_t`). Compression here is a **container-wrapper concern** (MAX/CBS-style archives), separate from any per-title encryption layer.

**Recommendation for Save Vault:** the generic/game-specific split maps directly onto a "PRESERVE ORIGINAL BYTES FIRST" default — Save Vault's snapshot layer should never assume it can decrypt, decompress, or "normalize" save contents before storing a snapshot. Even the *generic* algorithms (tier 1) are safe to use for integrity checksums (e.g., hashing a container for dedup/change-detection) but are not a license to transform stored bytes; and tier 2 (game-specific crypto) should never be attempted at all inside the snapshot path — decoding a specific title's save format, if ever wanted, belongs in a separate, explicitly-scoped, per-title research effort, not a general Save Vault capability.

## 8. Save patch engine findings

**Source:** `apollo-lib/docs/savepatch.rst` (header/syntax sections read), `apollo.h` (`apollo_apply_sw_code`/`apollo_apply_bsd_code`/`apollo_apply_py_code`/`apollo_apply_code` declarations), README claims for MicroPython/BSD.

- **`.savepatch` format:** plain-text, `;`-prefixed comment header (`;GameID` / `;Title` / `;Author`), a `:folder\file` target-file specifier supporting wildcards, then a body of Save Wizard/Game Genie-style codes. The parser is explicitly documented as tolerant of malformed input ("Unknown directives are ignored," "Malformed hex values may not be detected until patch application") — a permissive-parsing posture that is the **opposite** of EmuWiz's house fail-closed discipline seen throughout `docs/research/*` (e.g. the Amiga/Japanese-disk audits' repeated "refused, not guessed" pattern).
- **Save Wizard/Game Genie codes:** 14 code types (0-D per the README) — fixed-format binary patch opcodes (write byte/word/dword, conditional, increment, etc.). This tier is bounded and inspectable: a fixed opcode set with known semantics is auditable.
- **Bruteforce Save Data (BSD) scripts:** a richer scripting layer with data manipulation (set/write/search/insert/delete/copy) *and* transformation commands (encrypt/decrypt/compress/decompress) — i.e. BSD scripts can invoke the same generic-crypto tier from §7 as instructions inside a text patch file.
- **MicroPython scripts (`apollo_apply_py_code`):** apollo-lib embeds MicroPython v1.8.1 to run arbitrary `.py` save-patch scripts (confirmed via the README's "Python scripts via MicroPython v1.8.1" claim and the `docs/` directory containing MicroPython module reference pages — `docs/ucrypto.rst`, `docs/uzlib.rst`, `docs/uhashlib.rst`, etc. — which were listed but not individually opened). This is materially different from the fixed-opcode Save Wizard tier: **it is arbitrary code execution** over save-file bytes, gated only by the safety of the embedded MicroPython interpreter and whatever sandboxing Apollo itself applies (not established in this pass — apollo-lib is a library; sandboxing, if any, would be the embedding application's responsibility).

**Explicit recommendation, per task constraints:** do NOT propose adding a save-patch execution engine of any kind (fixed-opcode, BSD-script, or MicroPython) to EmuWiz without a strong sandbox story worked out first and separately. The permissive/tolerant parsing posture documented in `savepatch.rst` is itself a red flag for a project (EmuWiz) whose house style is fail-closed structural validation; if a patch format is ever wanted, it should be redesigned around EmuWiz's own validation discipline, not imported wholesale. This is stated here as a boundary, not a roadmap item.

## 9. Online save database findings (research only — not proposed for implementation)

**Source:** `apollo-saves` recursive tree listing (11,921 entries), README claims.

- **Structure (confirmed via tree):** top-level per-console directories (`PS1/`, `PS2/`, `PS3/`, `PSV/`, `PSP/`, `PS4/`), each containing per-title-ID subdirectories (e.g. `PS1/SLES03889/`, `PS2/SCAJ20066/`), each holding one or more `NNNNNNNN.zip` save archives, an `icon0.png`, and a `saves.txt` metadata file; a root `games.txt` (per console) catalogues titles. This matches the README's claimed structure exactly.
- **Provenance/trust model:** community-submitted via GitHub issues or external file-sharing links (README claim, not independently verified against actual issue history in this pass). There is no cryptographic signing of contributions, no per-save malware scanning evident in the repo structure, and — per §5 — a downloaded save must be *resigned* (identity fields rewritten) before use, meaning the database's trust boundary is "a community member says this save is legitimate and unmodified," backed by nothing structural.
- **Legal risk:** the database redistributes copyrighted game-save data (not game code/ROMs, but save files can embed licensed assets — character names, unlock states tied to a specific purchased copy, sometimes even asset fragments depending on the title) under GPLv3 licensing for the *tooling*, not necessarily a clear license for the *save content itself*. Mixing "how to parse a save format" (reimplementable, clean) with "here is a database of other people's save files" (redistribution of possibly-restricted content, unclear provenance) is a meaningfully different risk category.
- **Security risk:** ingesting arbitrary community-submitted binary blobs that are then loaded into an emulator's live game state is a real attack surface (malformed saves have historically been used as buffer-overflow vectors in emulated/real game code) — this is a generic "don't trust downloaded save files" concern independent of Apollo specifically.

**This audit does not propose that EmuWiz build, mirror, or integrate any online save database or downloader.** It is documented purely so that if the idea is ever raised, the trust/legal/security shape is understood in advance: community save databases are a fundamentally different risk tier than structural format-parsing knowledge, and adopting the *concept* (title-ID-keyed save repository) without Apollo's crowdsourced/unsigned trust model would require EmuWiz to invent its own provenance and vetting story from scratch — not a small undertaking.

## 10. Shared container model comparison

Apollo's PS1/PS2 card handling is the closest real-world analogue to EmuWiz's `SHARED_MEMORY_CONTAINER` principle, and it is useful precisely because Apollo does *not* follow that principle strictly — it treats the card as a container but freely extracts, deletes, and re-signs individual slots as first-class independent objects (`openSingleSave`/`saveSingleSave`, `toggleDeleteSave`, per-slot `formatSave`). That is the correct behavior for a *save-management* tool whose job is editing; it is explicitly **not** the correct behavior for a *preservation snapshot* tool, which is what Save Vault is.

What EmuWiz can safely take from Apollo's card model without importing its per-slot-mutation posture:

- **Container identity:** card container type (`ps1card.h` enum: raw/GME/VGS/VMP/MCX — the PS1 equivalents of "this container is a memory-card image, and specifically this dialect of one") is a legitimate thing for Save Vault to surface about a detected container, the same way EmuWiz already surfaces disk-image container type (D88/HDI/NHD/XDF/DIM) as a distinct evidence layer from platform/title identity (per `docs/research/JAPANESE_DISK_IDENTITY_AUDIT.md`'s layered model — container, geometry, filesystem, boot, family, exact software, DAT/hash).
- **Container size / slot count:** `PS1CARD_MAX_SLOTS = 15`, fixed 128 KB total — a shared-container snapshot in Save Vault could report "this card has 15 slots, of which N are occupied/deleted/corrupted" as descriptive metadata about the snapshot, without touching the snapshot unit itself.
- **Contained-save identity list:** per-slot region+product-code+identifier (PS1) or per-directory `icon.sys` title (PS2) is exactly the kind of "what games does this container currently hold" list a Save Vault UI could show *as read-only descriptive evidence about a snapshot*, classified per §6 (SUPPORTING_EVIDENCE, not proof) — this is corroborating detail, not decomposition.
- **Corruption/free-slot evidence:** the PS1 block-type enum (including `PS1BLOCK_CORRUPTED`) and PS2 ECC/cluster-check error taxonomy are good models for a "container health" summary Save Vault could attach to a snapshot (e.g., "3 of 15 slots read as corrupted at snapshot time," "ECC check failed on cluster N") — again, descriptive metadata about the atomic snapshot, never a trigger to split it.

**What must not be adopted:** Apollo's `openSingleSave`/`saveSingleSave`/`toggleDeleteSave`/per-slot `formatSave` pattern — i.e., treating an individual save *inside* a shared card as an independently snapshotted, independently restorable unit. That would directly violate `SHARED_MEMORY_CONTAINER`: the whole point of the principle is that restoring one save from an old snapshot while the card has since changed elsewhere can corrupt the card's internal consistency (cross-linked blocks, directory tables, free-space bitmaps) in ways a naive per-save diff cannot safely reason about — which is precisely why Apollo's own `mcio.h` exposes `mcio_mcCreateCrossLinkedFile` and multiple distinct backup-block-failure error codes: **card internal consistency is a real, structurally fragile property**, and that fragility is the argument *for* keeping the snapshot unit whole, not against it.

**Recommendation:** Save Vault's container detail view (phase 1/2 discovery+snapshot UI) can and should show container identity, size, contained-save count, contained-game identities (as evidence, labeled per §6's classification), free-slot/space info, and corruption warnings — all read-only description of one atomic snapshot. It should not expose "restore just this one save from this snapshot" as an operation; the restorable unit stays the whole container, consistent with the existing SHARED_MEMORY_CONTAINER rule. This recommendation only describes read-only descriptive UI for an already-atomic snapshot; it does not propose new parsing/restore code.

## 13. Licensing note

All three repositories are **GPL-3.0-or-later**, confirmed via the GitHub API `license.spdx_id` field for each repo and cross-checked against `apollo-lib`'s own `LICENSE` file content (standard GPLv3 text, fetched and matched). This has concrete consequences for EmuWiz:

- **Concepts, byte-offset knowledge, and format structure (what this document extracts) can be reimplemented independently without GPL obligation.** Facts like "PS1 header byte 0 encodes block type with these seven values" or "PSV container magic is `\x00VSP`" are not copyrightable expression — they are observations about a third-party file format (in most cases originally reverse-engineered by *other* projects Apollo itself cites, e.g. PSV-Exporter and CheatDevicePS2 per `ps2mc.h`'s own header comment, and `ps3mca-tool` per `mcio.h`'s header comment). EmuWiz can write its own clean-room parser from this knowledge with no licensing entanglement.
- **Copying Apollo's actual source (structs verbatim, function bodies, the specific C implementation) would impose GPLv3 obligations** on any component that links or embeds it — copyleft, source-availability, and license-compatibility requirements that would apply to the combined work. This audit copied zero lines of Apollo source into any EmuWiz file; every excerpt above lives only in this markdown document (research notes), not in `crates/`.
- **Apollo's own upstream attributions are relevant complications to note:** `mcio.h`/`mcio.c` is itself derived from `ps3mca-tool` (GPLv3, separate authors, attribution preserved in Apollo's header comment); `ps2mc.h`'s PSV/PSU/MAX/CBS struct definitions cite `PMStanley/PSV-Exporter` and `root670/CheatDevicePS2` as their format-reverse-engineering sources; `psv_resign.c` cites `ps3-psvresigner` by `@dots_tb`. None of these third-party sources' own licenses were independently checked in this pass — if EmuWiz ever wants to go beyond concept-level reuse (e.g., studying `ps3-psvresigner` directly for its AES/SHA1 salt-and-signature construction, briefly observed in `psv_resign.c`'s `generateHash()` using `mbedtls_aes_crypt_ecb`/`mbedtls_sha1_*` over hardcoded PS1/PS2 key material), that would require separately checking those upstream projects' own licenses before treating them as a citable source.
- **Dependency complications:** Apollo depends on PolarSSL/mbedTLS (Apache-2.0/GPL-dual-licensed depending on version — not verified here) and zlib (permissive) per `apollo-lib`'s README dependency list; these are standard, unencumbered choices and would not by themselves complicate an independent EmuWiz implementation using equivalent Rust crates (e.g. `sha1`, `aes`, `flate2` — already a dependency per the Amiga audit's ADZ findings).

**Bottom line:** everything recommended as HIGH VALUE / LOW RISK in §12 is concept-level (byte layouts, evidence classification, error taxonomy shape) and reimplementable clean-room with no GPL exposure. Nothing in this audit recommends vendoring or copying any Apollo source file.
