## 1. Purpose and scope

EmuWiz does not yet have an "Emulator Manager" feature — nothing in `crates/` checks for, downloads, updates, or channel-switches third-party emulator binaries beyond the existing one-shot managed-AppImage install path in `emulator_download.rs` (single version, no update check, no channel concept, no rollback). EmuHaven is the most mature open-source prior art for this exact feature area: a Python/CustomTkinter GUI that installs, updates, launches, and manages user data for Dolphin, Ryujinx, Xenia, and (historically) Yuzu, plus Switch firmware/keys and some direct ROM/save downloading.

This document extracts *workflow and architecture patterns* — not code — from EmuHaven's real source, classifies what is safe to draw on conceptually versus what must not be adopted, and proposes research-stage design sketches (channel model, portable profile concept, mod-install flow, community-save-import safety gate) for whoever designs EmuWiz's actual Emulator Manager next. Nothing here is a decision; it is raw material plus an honest risk read.

**Explicit non-goals, restated:** no downloader, no installer, no update-application logic, no mod installer, no save importer, no firmware/key downloader, no change to Save Vault or Publisher Profiles code (neither exists as implemented code — see §2).

## 3. Emulator install/update lifecycle findings

All four emulator runners share one shape: a `get_release`/`get_*_release` step (query GitHub Releases API or scrape a download-listing page for a regex-matched asset), a `download_*` step (plain HTTP GET with progress callback, `core/network/web.download_file_with_progress`), an `extract_*`/`install_*` step (zip or 7z extraction directly into the install directory), and separate `launch_*`, `delete_*`, `export_*_data`, `import_*_data`, `delete_*_data` methods. None of the four verify a cryptographic signature or a pinned checksum of the downloaded archive; verification is purely structural ("does this zip contain the expected executable path").

| Emulator | Source | Update-check | Verification before install | Install/overwrite behavior | Delete | Rollback on install failure |
|---|---|---|---|---|---|---|
| **Dolphin** | `dolphin/runner.py` | Scrapes `dolphin-emu.org/download/list/{master\|releases}/1/` for `.7z` files, regex-matches by OS/arch/channel (`_determine_release_regex`, lines 61-74); no local-vs-remote version *comparison* logic was found in this file — it fetches "the" release for the channel each time | `_verify_dolphin_archive` (line 52): for `.7z` it is **`return True` unconditionally** ("don't know how else to check if its valid for 7z" — literal code comment at line 53); for `.zip` it checks `'Dolphin.exe' in archive.namelist()` | `_extract_7z_archive` (line 136): if the install directory exists and is non-empty, a comment says "delete old installation... check for portable mode and temporarily move the user directory" followed by **`pass`** (lines 140-142) — i.e. the stated safety step is a no-op stub; the 7z is extracted directly into the existing directory, then files are moved out of the nested `Dolphin-x64/` subfolder into the parent, **overwriting any existing destination file** (`destination.unlink()` / `shutil.rmtree(destination)` before `shutil.move`, lines 167-175) | `delete_dolphin`: `shutil.rmtree(install_directory)` — no confirmation logic at this layer (presumably gated in the GUI, not traced) | None found — no backup of the pre-existing install directory before overwrite |

**Cross-cutting lifecycle findings:**
- **Atomicity:** none of the four extraction paths are atomic in the sense EmuWiz's `emulator_download.rs` already achieves (temp-file-then-hard-link-publish). Files are extracted or moved directly into the live install directory; a crash or power loss mid-extraction leaves a partially-overwritten installation with no recorded "this install did not complete" marker.
- **User-data vs executable-data separation:** clean at the path level for all four — executable/install data lives under `install_directory` (portable) or is fixed per-OS (`Dolphin.exe` next to install dir), while user data lives in a separately-resolved `get_user_directory()` (roaming AppData path, or a portable subfolder). This separation is a genuinely reusable *concept*, not code — see §7.
- **`delete_files_after_installing` setting** (default `True`, `settings.py` line 21): after a successful firmware/keys install, the downloaded archive is deleted (`firmware_archive.unlink()` in `firmware_keys_frame.py` line 144) — a storage-hygiene default, not a safety concern by itself, but it does mean there is no "keep last-downloaded installer for re-verification" trail.
- **`versions.json`** (`core/config/versions.py`): a flat `dict[str, str]` (e.g. `{"dolphin": "5.0-21000", "ryujinx_firmware": "18.0.0"}`) persisted as plain JSON, written via `set_version`/read via `get_version`. This is EmuHaven's entire "what did I last install" record — no timestamp, no source URL, no checksum, no previous-value history. `get_installed_version()` on each runner cross-checks this against **the executable's mere existence on disk** (e.g. Dolphin: `versions.get_version("dolphin") or "Unknown"` gated on `(install_directory / "Dolphin.exe").exists()`), not against the binary's actual contents — so a `versions.json` edited by hand, or a binary replaced out-of-band, would silently desync from the reported version with no detection.

## 4. Channel/build switching findings

- **Dolphin:** `release_channel` is a string setting (`"release"` / `"development"`), consumed by `_determine_release_regex` and `get_dolphin_release`'s `release_download_url_mapping` (`"development" → "master"`, `"release" → "releases"`, both mapped into the same `dolphin-emu.org` download-list URL template). Switching channel does not change the install path — both channels extract into the same `install_directory`, meaning **switching channel overwrites the other channel's binary** (no coexistence).
- **Xenia:** `release_channel` (`"master"` / `"canary"`) is the one emulator here with genuine directory-level channel isolation: `get_user_directory()`, `extract_xenia_zip_archive`'s target, `delete_xenia`, and `launch_xenia`'s exe path all key off `install_directory / release_channel`. Master and canary can coexist on disk simultaneously; switching the active channel in settings only changes which one launches next, not which ones exist.
- **Yuzu:** `release_channel` (`"mainline"` implied default / `"early_access"`), reflected in `get_installation_folder_name()` (`"yuzu-windows-msvc-early-access"` vs `"yuzu-windows-msvc"`) — like Xenia, each channel's *extracted folder name* differs, so on-disk coexistence is possible in principle, but `delete_yuzu`/`install_yuzu` still operate against `install_directory` as a whole and the settings model carries one `release_channel` value at a time, so the UI/workflow treats it as single-active-channel even though nothing prevents both folders existing under the same `install_directory`.
- **Ryujinx:** no channel concept found — one GitHub repo (`Ryujinx/release-channel-master`), one regex, one install path.
- **Config/save isolation across channels:** for Dolphin, `get_user_directory()` does not vary by `release_channel` at all — switching Dolphin's channel keeps the *same* user-data directory, so config/saves are automatically shared (not isolated) across release/development. For Xenia, `get_user_directory()` *is* channel-dependent (master gets `Documents/Xenia` or a portable `install_directory/master`; canary always gets `install_directory/canary`), so Xenia's two channels have genuinely separate user data. This inconsistency (Dolphin shares, Xenia doesn't) is itself worth noting — it is not a deliberate, documented design principle in the source, just what falls out of each `get_user_directory()` implementation.

**Reusable concept, not code:** the shape "channel is a config axis; some emulators key their entire user-data path off it, others don't" is a good cautionary example for EmuWiz's own channel design (§5): channel and user-data isolation must be an explicit, uniform decision per adapter, not an accidental byproduct of whichever engineer wrote that adapter's `get_user_directory()`.

## 5. Safe EmuWiz update model (concept only)

EmuHaven's model, as found in source, is: **fetch-latest-and-overwrite-on-demand**. There is a per-emulator "get the release for my channel" call, a structural verification of the downloaded archive, and an extraction directly into the live install directory — no staged install, no explicit before/after version comparison surfaced to the user as an approval gate, no atomic swap, no recorded rollback point. The `auto_emulator_updates: True` default setting name (confirmed present in `settings.py`; its consuming code path was **not traced** in this pass — flagged as unverified) suggests EmuHaven intends an even more automatic posture (check-and-prompt-or-apply near launch time), consistent with the repo's own description ("keep the emulator updated"), but this audit did not verify the exact trigger point.

A safer EmuWiz-side model, contrasted explicitly against that, and building on infrastructure EmuWiz **already has** (`emulator_download.rs`'s checksum + atomic-hard-link + `install.json` provenance path):

```
DETECT (installed version, from install.json provenance — not "file exists")
   -> CHECK UPDATE (query release source; compare against install.json version, not just "latest exists")
   -> SHOW VERSION/CHANNEL (installed vs available, explicitly, to the user — never silent)
   -> PREVIEW (what will change: archive size, target path, whether this is a downgrade,
               whether the channel is being switched, whether other channels/installs would be affected)
   -> USER APPROVAL (explicit action, not auto-apply — EmuHaven's default is the opposite of this)
   -> STAGED INSTALL (download + verify into a temp/staging location, same discipline
               emulator_download.rs already uses — never touch the live install dir first)
   -> VERIFY (checksum against a pinned/expected digest where available; EmuHaven has no
               digest check at all — this is a strict improvement, not a new idea, since
               emulator_download.rs already does this for the managed-AppImage path)
   -> SWITCH ACTIVE VERSION (atomic publish — same hard-link-publish pattern already in
               emulator_download.rs — only after verify succeeds)
   -> ROLLBACK AVAILABLE (previous install.json + binary retained, at minimum for one
               generation, so "switch active version" is reversible without a re-download)
```

**What evidence should be required before EmuWiz calls an update "successful"?** At minimum: (1) the downloaded archive's checksum matched an expected/pinned digest, or — where no digest is published upstream, exactly the gap `emulator_download.rs`'s `expected_sha256: Option<String>` already models honestly — the absence is surfaced to the user rather than silently treated as success; (2) the newly-published `install.json` records source URL, version string, and checksum (not just "did the file get written"); (3) the previous version's binary+`install.json` still exist on disk and are addressable for rollback; (4) — a genuinely new bar EmuHaven does not clear and that would need real design work, not just extraction to worry about — some minimal post-install sanity signal beyond "archive extracted" (e.g., the expected executable is present, is a regular non-symlink file, and is executable), which `emulator_download.rs`'s `install_appimage_at` already partially does for its narrower AppImage case.

This flow is **design-stage only** — it is not proposed as a spec ready for implementation, and no code implementing it exists or should be inferred from this section.

## 6. Side-by-side versions findings + relevance to EmuWiz

Only **Xenia** (master vs. canary, via separate subdirectories) and, more weakly, **Yuzu** (mainline vs. early-access, via differently-named extracted folders under the same `install_directory`, though the settings/workflow model still treats them as single-active-channel) support anything resembling side-by-side installs in EmuHaven. Dolphin and Ryujinx do not — switching channel/reinstalling overwrites in place. None of the four support **multiple versions of the same channel** side-by-side (e.g. two different Dolphin development builds); "side-by-side" in EmuHaven only ever means "two different channels," never "two pinned versions for rollback or comparison."

**Relevance to EmuWiz, as design-stage questions (not proposals):**
- **Launch Recipes:** if EmuWiz's Launch Recipe concept (referenced in existing diagnostics/profile infrastructure, not re-derived here) ever binds a recipe to a *specific emulator version* rather than "whatever is currently active," side-by-side version retention becomes a prerequisite — a recipe pinned to Dolphin 2024.1 must have Dolphin 2024.1 still installed and addressable, not silently replaced by whatever the channel's "current" build is.
- **Save Vault save-state compatibility:** save states are frequently emulator-version-sensitive (a savestate format can change between builds). If Save Vault ever needs to record "this snapshot was taken with emulator version X" as evidence (a question for Save Vault's own design, explicitly out of scope here), having the matching binary still installed and locatable is what makes that evidence actionable rather than purely informational.
- **Regression recovery:** EmuHaven's overwrite-on-update model means a user who updates into a regression has no built-in path back except re-downloading an older release manually. A version-retention model (§5's "rollback available") directly prevents this class of problem.
- **Per-game emulator-version override:** not found in EmuHaven at all — no per-title emulator-version pinning exists in any file read this pass. This would be a new EmuWiz concept, not an EmuHaven-derived one, if ever pursued.

## 7. Portable mode findings + PORTABLE EMULATOR PROFILE concept

**EmuHaven's portable mode is two distinct mechanisms that do not fully compose:**
1. **App-level portable mode** (`core/config/paths.py`): a `PORTABLE.txt` marker file in the current working directory, checked once at `Paths.__init__` time, switches the *entire application's* data directory from the OS user-data path (`platformdirs.user_data_path`) to `Path.cwd() / "portable"`. This is EmuHaven-the-app's own portability, not per-emulator.
2. **Per-emulator portable mode** (`settings.dolphin.portable_mode` / `.yuzu.portable_mode` / `.ryujinx.portable_mode` / `.xenia.portable_mode`, each a per-emulator boolean): changes `get_user_directory()` to resolve *inside* the emulator's own install directory (e.g. Dolphin: `install_directory / "User"`) instead of the OS roaming path. Dolphin and Xenia (master channel only) additionally **touch or unlink a `portable.txt` marker file inside the install directory itself at every launch** (`launch_dolphin` lines 220-223, `launch_xenia` lines 111-114) — this is the actual Dolphin/Xenia-native portable-mode convention (both emulators look for their own `portable.txt`/`Portable.txt` next to their executable), separate from EmuHaven's own `PORTABLE.txt`. Yuzu and Ryujinx instead rely on a fixed subfolder name (`user`/`portable`) existing or not, and **actively refuse to launch** if that folder exists but portable mode is toggled off and sync is disabled (`launch_yuzu` lines 81-85, `launch_ryujinx` lines 113-117) — a real safety check (avoid silently ignoring a user's portable data) that is a good pattern, not a code fragment.
- **Limitations found:** there is no unified "portable profile" object anywhere — portability is four separately-implemented per-emulator toggles plus one separate app-level marker, each with its own path-resolution quirks (see §4's Dolphin-shares/Xenia-doesn't-share inconsistency, which portable mode inherits). Nothing packages a portable install as a single exportable/importable unit; a "take this whole emulator+config+saves setup to another machine" workflow does not exist as a feature — a user would have to manually copy the install directory.

**PORTABLE EMULATOR PROFILE — concept only, no packaging implementation proposed:**

A future EmuWiz concept could unify what EmuHaven treats as four separate toggles into one addressable object:

- **binary/version** — the exact installed build + its `install.json`-equivalent provenance (source, checksum, install date) — this is the one piece EmuWiz already models better than EmuHaven's `versions.json`.
- **config** — the emulator's own settings/config files (paths, controller bindings, graphics settings) — EmuHaven's `USER_FOLDERS` constants (§9's mod-adjacent table) are effectively an unstructured allow-list for this today; a profile concept would want this typed, not just "a folder name string."
- **firmware metadata** — for Switch-class emulators, *evidence* that firmware/keys are present and which version (never the firmware/keys bytes themselves — see §11).
- **controller config** — currently bundled inside the generic user-data folder set in EmuHaven (e.g. Ryujinx's `profiles` folder), not modeled separately.
- **mods** — currently just another undifferentiated folder in EmuHaven's bulk copy list (§9) — a real portable profile would want mod identity/provenance, not just "whatever bytes are in this folder."
- **saves reference / Save Vault linkage** — EmuHaven copies save-bearing folders by raw path inclusion (no distinct "this is the save data" concept separate from "this is config"); a portable profile designed against EmuWiz's `SHARED_MEMORY_CONTAINER` principle would instead hold a *reference* to a Save Vault snapshot, not a raw copied folder, keeping saves and their provenance in Save Vault's domain rather than duplicating a second ad hoc copy mechanism.
- **launch recipe** — binding the above to a Launch Recipe (existing EmuWiz concept, not re-derived here) is the natural place a portable profile would plug in.

This is a naming/shape sketch for future design work, not a schema, packaging format, or implementation.

## 8. User-data import/export findings

All four emulators expose the identical three-method shape: `export_*_data(export_directory, folders, progress_handler)`, `import_*_data(import_directory, folders, progress_handler)`, `delete_*_data(folders_to_delete, progress_handler)`, all delegating to `copy_directory_with_progress`/`shutil.rmtree` in `utils/files.py` and `constants.py`'s per-emulator `USER_FOLDERS` list (Dolphin: 17 named folders; Xenia: 3 named paths including two `.toml` config files; Yuzu: 15 named folders; Ryujinx: 7 named folders/files including `Config.json`).

- **Overwrite behavior:** `copy_directory_with_progress` uses `shutil.copy2` per file with **no existence check on the destination file** — import silently overwrites any same-named file already present. There is no dry-run, no diff-preview, and no backup-before-overwrite step anywhere in this path.
- **Deletion behavior:** `delete_*_data` iterates the `USER_FOLDERS` constant (or a caller-supplied subset) and `shutil.rmtree`s each present folder — again no backup-before-delete, no trash/recycle-bin routing, no confirmation logic at this layer (presumably gated by a GUI-level `messagebox.askyesno`, consistent with the pattern seen in `firmware_keys_frame.py`'s reinstall-confirmation dialogs, but the actual delete-confirmation dialog code was not located/read this pass).
- **Path validation / traversal:** `copy_directory_with_progress`'s `include`/`exclude` filtering only matches against `file.parts` (a simple substring-of-path-components check) — it does not validate that `export_directory`/`import_directory` themselves are sane, non-traversal-y user input; that validation, if any, lives in whatever GUI dialog collects the directory (e.g. `gui/windows/path_dialog.py`, not read this pass). **Not independently verified as safe or unsafe** — flagged as unverified rather than assumed either way.
- **Archive handling:** none — import/export operates on raw directories, not archives; there is no zip/tar packaging step for user-data export/import at all (in contrast to firmware/keys/emulator-binary installs, which are all archive-based).
- **Sync-on-launch variant:** a separate, riskier pattern exists in `launch_dolphin`/`launch_yuzu`/`launch_ryujinx` — if `sync_user_data` is enabled, the *previous* launch's data path is diffed against the *current* one and `shutil.copytree(..., dirs_exist_ok=True)`'d over automatically at every launch (Yuzu/Ryujinx additionally `shutil.rmtree` the old path afterward — a move, not a copy). This runs with no user-visible preview and no backup, every single launch where the two paths differ.

**Should EmuWiz use Save Vault primitives for emulator-user-data migration instead of a separate copy/import subsystem? — Yes, provisionally, with reasoning:**

EmuHaven's `copy_directory_with_progress`/`delete_*_data` pattern is exactly the kind of unstructured, no-backup, no-provenance, silent-overwrite subsystem that a `SHARED_MEMORY_CONTAINER`-disciplined design should avoid reinventing. The prior Apollo Save Tool audit (§10 there) established that Save Vault's restorable unit should stay whole and atomic, with descriptive read-only metadata layered on top rather than per-item decomposition. Emulator user-data directories (an entire Ryujinx `bis/`+`system`+`profiles` tree, a Dolphin `User/` folder) are structurally the same kind of object as the shared memory-card containers that audit discussed: a bundle of config, save state, and metadata that is fragile to partially overwrite and easiest to reason about as one atomic unit with a snapshot history. Concretely, if EmuWiz's Emulator Manager needs "move my Ryujinx data to a new machine" or "back up before an update," reusing Save Vault's snapshot/restore primitives (whatever they turn out to be) for that job — rather than building a second, parallel `copy_directory_with_progress`-style subsystem — avoids exactly the failure mode EmuHaven has today (no backup-before-overwrite, no history, no provenance). The one caveat: Save Vault's `SHARED_MEMORY_CONTAINER` principle was designed around *save* containers specifically; an emulator's full user-data tree also contains non-save data (graphics config, controller bindings, UI prefs) that arguably doesn't belong in a save-snapshot system at all. This audit does not resolve that boundary — it is a real open design question for whoever builds Save Vault and the Emulator Manager, not something EmuHaven's source can answer, since EmuHaven doesn't distinguish "save" from "config" within a user-data folder either.

## 9. Mod installation findings + proposed EmuWiz flow (concept only)

**Real finding, stated plainly: EmuHaven does not have a mod installer.** `src/gui/frames/my_switch_games_frame.py` has a "Download Mods" button wired to `download_mods_button_event` → `open_mod_downloader(game)`, and `open_mod_downloader`'s entire body, verbatim, is:

```
def open_mod_downloader(self, game):
    pass
```

This is a stub. The only place "mods" appears elsewhere in the codebase read this pass is as one undifferentiated entry in Ryujinx's `USER_FOLDERS` constant (`["bis", "games", "mods", "profiles", "sdcard", "system", "Config.json"]`) — meaning a Ryujinx `mods/` folder is only ever bulk-copied/deleted along with every other user-data folder via §8's generic import/export/delete methods, with **no discovery, no per-mod identity, no install/enable/disable/uninstall workflow of any kind**. There is no mod installation architecture to extract concepts from here — this is the audit's most direct "the README implies more than the source delivers" finding, worth stating as clearly as the honesty standard in the Apollo audit demands.

**Proposed EmuWiz flow — concept only, informed by the *absence* above plus general good practice, not derived from EmuHaven code:**

```
DISCOVER (what mods exist for a matched game — source TBD, out of scope here)
   -> MATCH GAME IDENTITY (reuse EmuWiz's existing game_identity.rs evidence model,
               per the same reasoning as the Apollo audit's §11 — never invent a parallel
               identity system for "which game is this mod for")
   -> INSPECT MOD (what files/paths would this mod touch, what does the archive contain)
   -> PREVIEW FILE OPERATIONS (explicit list of adds/overwrites before anything happens —
               a preview EmuHaven's own copy_directory_with_progress never offers)
   -> SNAPSHOT/BACKUP EXISTING TARGET (before touching anything a mod would overwrite —
               the missing step in every EmuHaven import/overwrite path in this audit)
   -> APPLY
   -> VERIFY (did the expected files land where expected)
   -> ENABLE/DISABLE/ROLLBACK (an explicit on/off + undo, which requires the snapshot step
               above to actually exist and be addressable)
```

Design-stage only; not a spec, not a format, not an implementation.

## 10. Community-save import findings, compared against the Apollo Save Tool audit

**This is implemented in EmuHaven**, unlike mods. `SwitchEmulator.get_saves_list()` (static method, `switch_emulator.py` lines 314-324) lists files at a fixed GitHub path (`NXResources/NX_Saves`, path `nintendo/switch/savegames`) via `get_file_list`/the GitHub Contents API; `SavesBrowser` (`gui/windows/saves_browser.py`) presents that list as buttons; clicking one downloads the raw file (`GitHub.RAW_URL` template) straight to **`Path.home() / "Desktop" / save`** — not into the emulator's save directory at all. The dialog's own instructional text (lines 35, quoted verbatim): *"Once the download is complete, the save file will be placed on your desktop. To install a save, right click the game in the emulator game list, 'open save folder' and extract the downloaded archive there. Be sure to backup your current save file if you want to use it later!"*

So the actual mechanism is: **download to Desktop, tell the user to manually extract it into the right folder themselves, and manually remind them (in a text label, not an enforced step) to back up first.** There is no automatic destination resolution, no automatic extraction, no overwrite handling by EmuHaven itself (any overwrite happens if/when the user manually extracts over their existing save), no account/user binding check, no checksum/integrity check of the downloaded save, and no provenance tracking beyond "this came from the `NXResources/NX_Saves` GitHub repo" (itself a community-maintained, unsigned save collection — structurally the same trust-tier problem the Apollo audit's §9 flagged for `bucanero/apollo-saves`: community-submitted binary blobs with no cryptographic signing, about to be loaded into a live emulator's game state).

**Cross-reference to `APOLLO_SAVE_TOOL_AUDIT.md` (read for this comparison, not modified):** that audit's §9 concluded a community save database is "a fundamentally different risk tier than structural format-parsing knowledge" and explicitly recommended against EmuWiz building or integrating one. EmuHaven's implementation reinforces that conclusion from a different angle: even a *working, shipped* community-save-import feature (EmuHaven's, unlike its mod downloader) still offloads every actual safety step — correct destination, backup, overwrite awareness — onto the user via an instructional label, because the alternative (EmuWiz or EmuHaven doing it automatically) requires exactly the trust/provenance infrastructure neither project has built.

**Proposed safety gate for EmuWiz, if a community-save-import feature is ever pursued (concept only, same posture as the Apollo audit's own recommendation not to build this without one):**
- Proven game identity (EmuWiz's own evidence model, not a filename match) before offering any save as a candidate for a given game.
- Archive-traversal checks on extraction (EmuHaven relies on stdlib `zipfile.extract`'s built-in path-sanitization and performs no additional check of its own — not proven unsafe, but not an explicit, audited guarantee either).
- Explicit preview of what would be overwritten, before extraction — never EmuHaven's "we told you to back up in a text label" pattern.
- A pre-import Save Vault snapshot taken automatically, not left to the user to remember.
- Account/binding compatibility check where the platform has one (Switch saves are less strongly account-bound than the PS4 case in the Apollo audit, but this was not independently verified for Switch in this pass).
- No arbitrary script/patch execution of any kind (this rules out ever adopting anything resembling Apollo's BSD/MicroPython save-patch tier, which EmuHaven does not have either — a non-finding worth stating so it isn't assumed present).

## 11. Firmware/keys findings — DETECT/VERIFY/GUIDE vs DOWNLOAD/DISTRIBUTE

**EmuHaven actually implements the DOWNLOAD/DISTRIBUTE tier, not just DETECT/GUIDE, and this is the single highest legal-risk finding in this audit.** `SwitchEmulator.get_firmware_keys_dict()` (`switch_emulator.py` lines 245-304) queries **all releases** of `NXResources/NX_FK` (`constants.Switch.FIRMWARE_KEYS_GH_REPO_OWNER/NAME`) via the GitHub Releases API, and `firmware_keys_frame.py`'s `install_firmware_handler`/`install_keys_handler` download the matched asset directly via `download_firmware_release`/`download_keys_release` (plain HTTP GET) and extract it into the emulator's firmware/key directories. `NXResources/NX_FK` — based purely on its name and EmuHaven's own asset-naming convention (`"Alpha"`→firmware, `"Beta"`→keys, a deliberately obfuscated naming scheme, per `get_firmware_keys_dict`'s `convert_to_title`/asset-filtering logic) — is a third-party GitHub repository apparently hosting actual Nintendo Switch firmware and cryptographic key material for redistribution. **This audit did not open that repository or its contents** (out of scope, and doing so would not change the legal analysis); the naming-obfuscation pattern in EmuHaven's own code (renaming "Alpha"/"Beta" assets to "Firmware"/"Keys" on the fly) is itself a signal that this is understood, internally, as sensitive/likely-infringing content.

**Verification found:** purely structural, same tier as every other archive check in this audit — `verify_firmware_archive` checks every entry in the zip ends in `.nca`; `verify_keys` checks for the literal presence of a `title.keys`/`prod.keys` file (or, for a raw `.keys` file, does no content check at all beyond the filename). No signature check, no hash pinning, no cross-check that the *content* of `prod.keys` is plausible key material versus arbitrary bytes with the right filename.

**Explicit classification for EmuWiz:**
- **DETECT** (is firmware/keys present, which version — via `check_current_firmware`/`check_current_keys`/`get_installed_firmware_version`/`get_installed_key_version`, all read-only filesystem checks) — this tier is safe to draw on conceptually; it's the same shape as EmuWiz's own Doctor `discover_*_profiles` read-only evidence model.
- **VERIFY** (structural: is this a well-formed firmware/key archive) — safe concept, though EmuHaven's own implementation is weak (extension/filename checks only, no content or signature validation) and should not be copied as-is even conceptually.
- **GUIDE** (tell the user where firmware/keys go, how to obtain them themselves, from their own console) — not implemented by EmuHaven at all in the files read this pass; EmuHaven skips straight past guidance to direct download.
- **DOWNLOAD/DISTRIBUTE** (fetch and install the actual firmware/key bytes from a third-party redistribution repo) — this is what EmuHaven does, and it is **explicitly the tier EmuWiz should not adopt**. Firmware and console-derived key material are not the kind of thing a clean-room reimplementation or "concept-level reuse" argument (as used for file-format knowledge throughout this audit and the Apollo one) can launder — they are the copyrighted/DRM-protected bytes themselves, not a format description of them.

**Recommendation:** EmuWiz should not become a firmware/key distribution service, full stop. If a Switch-class emulator adapter is ever added to EmuWiz's scope, the firmware/keys story should stop at DETECT (does the user already have firmware/keys installed, from wherever they legitimately obtained them) and, at most, GUIDE (point at the emulator's own official documentation for legitimate acquisition), never DOWNLOAD.

## 12. Game download features — architectural-only audit

EmuHaven has direct ROM-download functionality for two of its four emulators, built on scraping **Myrient** (`myrient.erista.me`), a public file-index mirror: `constants.Dolphin.MYRIENT_GAMECUBE_PATH`/`MYRIENT_WII_PATH` and `constants.Xenia.MYRIENT_XBOX_360_PATH`/`MYRIENT_XBOX_360_DIGITAL_PATH` point at specific No-Intro/Redump-organized paths on that mirror; `core/network/myrient.py`'s `get_list_of_games`/`get_game_download_url` scrape a directory listing page and construct direct `.zip` download URLs by URL-encoding the game name.

**Per the task brief, this audit deliberately does not detail the download mechanism itself further, and classifies the download capability itself as DO_NOT_ADOPT** — EmuWiz downloading copyrighted game ROMs from a third-party mirror is squarely out of scope and legally the wrong direction for this project regardless of how EmuHaven implements it.

**Adjacent UX concepts, at an architectural level only, that could be reused for entirely legitimate purposes (e.g. downloading a user's own legally-obtained content, or unrelated non-copyrighted assets like box art) without adopting the ROM-download mechanism itself:**
- A consistent progress-handler abstraction (`ProgressHandler`/`progress_handler.start_operation(title, total_units, units, status)`) threaded through every long-running operation in the codebase (downloads, extractions, copies, deletes) — one shared progress-reporting shape reused everywhere, which is a reasonable UX pattern independent of what's being downloaded.
- Explicit "source" labeling in UI text (e.g. the SavesBrowser dialog naming exactly where a save came from) — a provenance-display habit worth keeping regardless of source, though EmuHaven's own execution of it (a text label, not structured metadata) is weak and shouldn't be copied as the target bar.
- A caching layer (`self.cache.get_json`/`add_json`/`get_file`/`add_file` with TTLs, seen wrapping firmware/keys metadata and TitleDB lookups) — cache-with-TTL for slow/rate-limited metadata lookups (e.g. GitHub API release listings) is a reasonable general pattern, independent of what's cached.

## 13. Security review — minimum EmuWiz safety rules

Findings from this pass, generalized into rules, independent of whether EmuWiz ever builds any of the features above:

1. **Never install a downloaded executable/archive without checksum verification against a pinned or fetched digest**, and be honest in the UI when no digest is available (EmuWiz's `emulator_download.rs` already does this — `expected_sha256: Option<String>` — EmuHaven never does, for any of the four emulators, firmware, keys, or saves).
2. **Never overwrite a live install/user-data directory in place.** Stage first, verify, then atomically publish (EmuWiz already does this for managed AppImages; EmuHaven never does, for any of its extraction/copy/sync paths).
3. **Treat archive extraction as untrusted input.** EmuHaven relies entirely on Python stdlib `zipfile`'s built-in path-sanitization with no additional traversal check of its own, across every extraction path in this audit (emulator binaries, firmware, keys, mods-that-don't-exist, user-data-that-isn't-archived). This was not proven unsafe in this pass, but "we rely on the standard library's default behavior and never checked" is not the same as "we verified this is safe" — EmuWiz should do the latter explicitly wherever it extracts anything.
4. **Never auto-copy/auto-sync user data across paths without a preview and a backup**, the pattern found in `launch_dolphin`/`launch_yuzu`/`launch_ryujinx`'s `sync_user_data` behavior — a silent `shutil.copytree`/`shutil.rmtree` pair on every launch with no user-visible preview.
5. **Never download or redistribute firmware/keys** (§11) — DETECT/GUIDE only, never DOWNLOAD, for this specific content class.
6. **Never download or redistribute copyrighted game content** (§12) — out of scope entirely, not a DETECT/GUIDE question at all.
7. **Never run arbitrary scripts over save or mod content** — not present in EmuHaven (no finding to report here), but worth stating as a standing rule given the Apollo audit's parallel finding for save-patch scripting.
8. **Record real provenance on every install** (source URL, version, checksum, install timestamp) rather than a bare version string (EmuHaven's `versions.json`) — again something EmuWiz's `install.json` pattern already does better; keep doing it as the Emulator Manager grows.
9. **HTTPS/source provenance:** all EmuHaven network calls observed in this pass (GitHub API, `raw.githubusercontent.com`, Myrient, `dolphin-emu.org`) use HTTPS URLs; no plaintext-HTTP download path was found in the files read. Not independently verified for every file in the tree.

## 16. Proposed Emulator Manager roadmap (research/design only — no implementation)

Adjusted from the task brief's implied phase shape in light of what this research actually found — in particular, that EmuWiz already has a stronger install primitive than EmuHaven (atomic + checksummed), so the roadmap should front-load *update-detection and approval UX* rather than re-deriving install safety EmuWiz already has:

- **Phase E0 — Research/capability matrix.** This document is a contribution to E0, not a replacement for it. E0 should also cover: what update-check sources exist per emulator EmuWiz might target (GitHub Releases API is the dominant pattern per this audit, but Dolphin's own download-list-page scrape is a real alternative shape worth a second look), and a clear map of which emulators in `emulator_download.rs`'s existing `EmulatorDownloadSpec` catalog (`retroarch`, `pcsx2`, `ppsspp`, `rpcs3`, `duckstation`, `xemu`, `dolphin`, `scummvm`, `shadps4`) actually publish stable, checksummable release assets versus rolling/nightly-only builds.
- **Phase E1 — Update detection.** DETECT + CHECK UPDATE only (§5's first two stages), read-only, no install action — surface "an update is available" as evidence, the same posture as Doctor's existing read-only discovery model.
- **Phase E2 — Approval + staged install.** PREVIEW → USER APPROVAL → STAGED INSTALL → VERIFY, built directly on the existing `download_and_install_resolved`/checksum/`install.json` machinery rather than a parallel path.
- **Phase E3 — Version retention + rollback.** SWITCH ACTIVE VERSION → ROLLBACK AVAILABLE — the one genuinely new storage-model piece (keeping N-1 alongside current).
- **Phase E4 — Channel model.** A uniform, explicit channel abstraction (learning from §4's Dolphin/Xenia inconsistency) — deliberately placed *after* E1-E3 land for single-channel emulators, so channel complexity doesn't block basic update-detection value.
- **Phase E5 — User-data migration.** Framed per §8 as a Save Vault extension question first; this phase should not start until that framing question has an answer, to avoid building an EmuHaven-style parallel copy subsystem that then has to be reconciled with Save Vault later.
- **Phase E6 — Portable emulator profiles.** The unifying concept from §7, deliberately last — it composes binary/version (E1-E3), channel (E4), and user-data (E5) into one object, so it cannot usefully be designed before those exist.

Explicitly not included at any phase: mod installation (§9 — green-field, no EmuHaven prior art to lean on, would need its own dedicated research pass first), community-save import (§10 — gated behind Save Vault existing and its own safety-gate design), firmware/key downloading (§11 — permanently out of scope for the DOWNLOAD tier), and game/ROM downloading (§12 — permanently out of scope).

## 17. Explicit DO-NOT-ADOPT list (consolidated)

- Firmware/key **downloading or redistribution** from any third-party mirror repository (§11) — DETECT/GUIDE only, if ever in scope at all.
- Game/ROM **downloading** from Myrient or any similar mirror (§12).
- EmuHaven's **unverified, unstaged, in-place overwrite** pattern for emulator binary installs and user-data sync (§3, §8) — EmuWiz already does better; do not regress toward this pattern for convenience.
- EmuHaven's **silent auto-sync-on-launch** of user data between paths with no preview (§8, `sync_user_data`).
- EmuHaven's **community-save-import-with-no-safety-gate** pattern (§10) — download-to-Desktop-and-hope is not a bar to meet, only a bar to exceed if this feature is ever pursued at all.
- Any **save-patch scripting engine** (fixed-opcode, script, or otherwise) — not found in EmuHaven, but restated here per the parallel Apollo audit finding, since firmware/mod/save features are adjacent enough that the temptation could recur.
- Treating a **filename or extension check as verification** — EmuHaven's structural-only archive checks (`.nca` extension presence, expected-exe-in-namelist) are the wrong bar; EmuWiz's existing checksum-based verification in `emulator_download.rs` is already the right one — do not weaken it to match EmuHaven's for any new adapter.
- Building a **second, parallel user-data copy/import subsystem** alongside Save Vault once Save Vault exists (§8) — resolve the Save Vault-extension question first.
